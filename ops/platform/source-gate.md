# Source candidate publication

The [single-operator release policy](../../docs/api-integration/release-policy.md) supersedes the November 1 external signing procedure. Dardan's authenticated manual workflow dispatch approves building the specified source revisions. No separate approval key, identity enrollment, signed permit, GitHub App or GitHub environment reviewer is required.

## One-time preparation

1. Register the manual workflow on the frontend default branch first: GitHub requires the file on `main` even when dispatch selects `staging`. The minimal [registration PR #57](https://github.com/princessdardan/lash-her-frontend/pull/57) contains an inert default-branch entry with no permissions or credentials; running that entry refuses with guidance to select the reviewed staging coordinator. It also prevents automatic Vercel releases on `main`/`staging`, preserving existing cron definitions. A staging-only merge cannot perform this registration. See [GitHub manual-dispatch requirements](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow).
2. Publish/review the prepared source and CI changes in all three repositories. Private APIs use `main`; the frontend coordinator may use `staging` or `main`. No API staging branches are required. All selected heads must have passing CI.
3. Configure frontend repository Actions secret `PLATFORM_SOURCE_READ_TOKEN` with a fine-grained token limited to these three repositories: Contents read, Actions read, automatic Metadata read. Keep its value private and set an expiry. The existing compatibility workflows also need that same credential stored as `CROSS_REPO_READ_TOKEN` in both API repositories. These are three storage locations for one read-only credential. No cloud/database/package permission is needed. Registry writes use `GITHUB_TOKEN` separately.
4. Confirm the candidate GHCR packages are scoped correctly and private API images remain private. Native branch protection is useful where supported but is not required to buy or configure additional services.

## Each candidate

1. In frontend Actions, manually run **Platform artifact candidate** as `princessdardan`, choosing the frontend coordinator branch (`staging` or `main`; private APIs use `main`) and the exact three reviewed commit IDs. The frontend commit must match the workflow revision. This dispatch is the build approval; there is no second approval click.
2. The workflow verifies the canonical operator/repository/run, current branch heads and latest passing CI jobs, verifies the released Course–Community contract against the exact selected checkouts, then builds six immutable AMD64 artifacts. It scans exact digests, verifies native provenance/SBOMs, exercises the integration harness and records fresh source/CI evidence.
3. Use only a successfully qualified candidate. Retain its manifest and receipt with the release. A failed candidate is never deployable. A build rerun is allowed after checking the cause and revalidates current evidence. A failed migration is different: inspect database state before any deliberate retry.
4. Run staging through the operator release procedure. Production promotes the same verified artifacts after staging and its production checks. Artifact publication grants no deployment or migration permission.

Every image retains its raw exact-digest scan before qualification. The gateway and frontend migration images use the selected frontend's native-runtime verifier. Course runtime/migration and Community runtime/migration use `ops/runtime/verify.mjs` from their own exact selected API checkouts. Each verifier independently rebuilds the locked native package, checks the installed library and regression, and produces a runtime SBOM, build/image verification record, digest/package-bound OpenVEX `fixed` statements and the enforced filtered scan. Raw scans collect all packages; unrelated HIGH/CRITICAL findings still fail. There are no broad ignores or severity waivers.

Before accepting any API artifact, the collector verifies the clean exact source checkouts and invokes that API's `--recorded` CLI with the same source directory. It validates the retained raw/filtered scans, SBOM, VEX and native proof against that repository's `ops/runtime/inputs.lock.json`; missing, forged or mismatched evidence refuses collection. BuildKit provenance, SPDX SBOMs and GitHub attestations remain separately required and bound to the selected repository, commit and immutable image digest. Per-image runtime artifacts are retained even when qualification refuses; the successful candidate artifact retains all evidence. Candidate preparation does not deploy or constitute staging acceptance.

New P2 candidates use source proof version 4 and add `contractPhase: "p2"` / `phase2ContractManifestSha256`. `contractManifestSha256` and API migration `contractSha256` still identify the immutable v1 bundle. The source gate requires a reviewed `released` P2 manifest, verifies its three artifact revision pins against the selected Course/Community commits and compares the exact API contract bytes before image publication. The frontend SQL image packages the P2 manifest, four JSON artifacts and README; its source inventory binds every file. The separate P2 hash follows the candidate, frontend migration artifact/job, schema summary and database/terminal receipts. New P2 source cannot enter historical P1 recovery by omitting these fields. Historical v3/P1 proofs and receipts keep their original source and v1 hash semantics.

The released label also requires the fixed [exact compatibility review](../../docs/api-integration/contract-compatibility-review.md). Its Git blob must match the selected frontend commit, its baseline must match the actual archived released bundle, and every normalized wire delta must match the recorded before/after hashes. The enrollment event remains byte-identical; only an explicitly mapped boundary `info.title` change is permitted. The SQL image packages and hashes this review and both verifier modules. The existing source revision binds the review under the single-operator release policy.

Native qualification jobs use the explicit `ubuntu-24.04` runner baseline. Ubuntu 26.04 produced a failed independent reference build while the same-source initial Buildx image build passed; separate diagnostics observed denied self-signaling in that reference context. The precise kernel or sandbox cause remains unproven. Qualification still requires the original exact abort/assertion negative control, all patched checks and the ordinary enforced scan. Runner selection does not change the native source, signal predicate, runtime capabilities or security options.

Owned PostgreSQL source rehearsals mount the actual source, scripts, package/TypeScript configuration and both unchanged contract directories read-only. The protected probe eagerly imports the legacy and P2 response validators, so mounting only the v1 manifest leaves required legacy JSON files unavailable. These source-fixture mounts do not expand the minimal SQL image payload.

`node --test ops/platform/artifact-candidate.test.mjs ops/platform/platform.test.mjs ops/platform/source-checkout.test.mjs ops/platform/patched-runtime.test.mjs` checks the collector and workflow with owned evidence fixtures. To also exercise the actual API `--recorded` CLIs, set `PLATFORM_TEST_COURSE_SOURCE` / `PLATFORM_TEST_COMMUNITY_SOURCE` to their clean local checkouts and `PLATFORM_TEST_COURSE_COMMIT` / `PLATFORM_TEST_COMMUNITY_COMMIT` to the exact 40-character revisions. Those cases verify source cleanliness before and after, run all four API prefixes and refuse a wrong source lock, absent image digest and missing VEX. They use disposable fixture evidence and leave the API checkouts unchanged; they do not build, scan or qualify registry images.
