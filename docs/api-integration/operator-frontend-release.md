# Frontend provider release component

`ops/platform/host/vercel.py` implements provider operations for the unfinished parent frontend/API release coordinator. It has no standalone command or automatic activation. The [single-operator release policy](release-policy.md) remains authoritative; this component does not bypass required frontend suspension or qualify a release.

## Implemented operations

- `disable_schedules` verifies the exact environment's fixed project, team and connected frontend repository, disables native crons with the provider API and reads back the disabled state. It refuses an unrelated production-target change. It does **not** claim running invocations, callbacks, historical deployment URLs or database writers are drained. Its result always reports `frontendQuiescenceVerified=false`.
- `stage_frontend` uses the selected project's **Production target** for its environment configuration. Business staging selects the dedicated staging project; production selects the separate live project. It builds remotely from the exact reviewed Git commit, without pulling secrets or uploading a local checkout. It sets `autoAssignCustomDomains=false`, then verifies the returned deployment's project, Git repository/commit, release identity and ready state while checking the existing production target and disabled-cron state remain unchanged.
- The remote build has an exclusive durable intent before creation, a separately retained deployment ID as soon as one is returned, and a sanitized outcome. Neither errors nor observation timeouts retry creation, promote, roll back, enable schedules or admit traffic. An uncertain POST requires provider inventory/reconciliation. An observation timeout retains the existing deployment ID for subsequent inspection; it does not mean the remote build stopped.
- `promote_frontend` rechecks the staged Production-target build's exact project/source/release identity and requires the parent's live frontend verification callback before requesting domain promotion. It refuses active alias jobs, rolling-release configuration, enabled schedules or a changed production target. It rechecks provider state after the callback, records an exclusive intent, and sends one promotion request for the retained deployment ID. Completion requires a newer successful `lastAliasRequest` for that exact deployment and the matching production target. HTTP acceptance or a changed target alone is insufficient. Empty201/202 acknowledgement bodies are accepted only for this exact reviewed endpoint; every other response still requires a bounded JSON object. Promotion-state queries explicitly request `rollbackInfo=true` so the provider returns `lastAliasRequest`.
- `observe_frontend_promotion` resumes observation of the recorded promotion using GET requests only. An uncertain POST or observation timeout never causes another POST, rollback, cron enablement or gateway admission. Observations have separate durable records and preserve the original mutation outcome. Uncertain records use `frontendDomainsPromoted=null`; only verified completion sets it to true. Both `trafficAuthorized` and `gatewayTrafficAuthorized` remain false because domain promotion does not authorize gateway writes.
- The [frontend workload probe](operator-frontend-workload-probe.md) now supplies a real HTTP verification callback. It automatically configures an expiring sensitive credential in the existing project before the build, then checks the pinned deployment through its SDK-authenticated gateway catalog request. It consumes existing automation protection access privately, preserves `CRON_SECRET` and requires no new operator credential. Owned fixtures verify its control flow; deployed workload OIDC remains unqualified.

The parent supplies its scoped provider credential privately at runtime. The client fixes the HTTPS API origin and team, verifies TLS, disables ambient proxies and redirects, bounds response sizes and replaces provider exception details with fixed diagnostics. Provider responses may contain environment/protection data; they are never persisted. Common records retain selected identities/results only. No environment-variable values or authentication files are read by this component.

## Integration still required

The [initial staging coordinator](operator-staging-qualification.md) connects candidate checks, the three database stages, verified API startup, probe preparation, pinned build, workload verification and domain promotion. The API coordinator's trusted `after_runtime_ready` continuation retains the shared lock throughout those provider operations; callback failure stops the API runtime and preserves separate failure evidence. Pending frontend SQL still requires actual writer/scheduler suspension and is refused by that initial command. An already-current frontend instead passes the migration image's read-only lineage/schema/grant verification before either API migration; that verification does not prove producer suspension. Producer restoration, native scheduling qualification, final admission and production orchestration remain unfinished. All remaining initial P1 live evidence is still required. A build returning `FRONTEND_STAGED` always has `trafficAuthorized=false` and `promotionAuthorized=false`.

The existing host full-bundle CLI refuses pending frontend SQL without the reviewed quiescence coordinator. Its already-current read-only path still leaves frontend deployment and acceptance unfinished. Do not wire `disable_schedules` directly into the quiescence callback: future schedule cancellation alone cannot prove suspension of all writers. Project pausing is also insufficient evidence of in-flight or historical-deployment drain.

## Verification and provider references

The host suite exercises these operations through an owned HTTPS server and fixture CA with synthetic credentials. It covers exact source/target selection, schedule-disable readback, production-target drift, TLS refusal, redirect refusal, error redaction, bounded responses, uncertain creation, failed builds and observation timeout/handle retention. Promotion cases also cover callback-before-mutation ordering, missing/failed verification, preview-build refusal, active/unrelated/failed alias jobs, stale completion evidence, HTTP 201/202 acceptance, rolling-release refusal, read-only continuation and credential-free records. These are real HTTP/TLS exchanges with controlled provider responses, not live Vercel qualification.

Provider semantics were checked against [Vercel deployment creation](https://vercel.com/docs/rest-api/deployments/create-a-new-deployment), [deployment inspection with Git metadata](https://vercel.com/docs/rest-api/deployments/get-a-deployment-by-id-or-url), [CLI skip-domain behavior](https://vercel.com/docs/cli/deploy#skip-domain) and [Vercel's cron-control client](https://github.com/vercel/terraform-provider-vercel/blob/main/client/project_crons.go). The installed official Vercel CLI 50.0.0 maps `--skip-domain` to `autoAssignCustomDomains=false`; the component uses that request field directly. The connector's project metadata response omits the full Git/cron/production-target state, so it cannot supply the complete verification required by this component.

Promotion semantics and selected job fields are verified against [the native promotion API](https://vercel.com/docs/rest-api/projects/point-production-traffic-to-a-given-deployment), [project metadata](https://vercel.com/docs/rest-api/projects/find-a-project-by-id-or-name) and the installed official Vercel CLI 50.0.0 promotion/status implementation. The component requires an ordinary complete promotion; it does not configure or operate rolling releases.

Dardan has supplied the runtime/release credential handoff and the mounted frontend `.env` injection path. A private, read-only check verified the injected `VERCEL_TOKEN` can read the exact staging project/team/repository; OIDC is enabled, native crons remain enabled, and no rolling-release configuration or prior alias request was present at observation. No decrypted environment-variable values or full provider responses were displayed. This verifies staging metadata access, not mutation permissions or release readiness. No live Vercel mutation, deployment or database migration was performed while developing or testing this component.


## Deliberate recovery after a reconciled promotion

The [staging promotion recovery component](operator-staging-promotion-recovery.md) can restore the same eight stopped containers only after successful database receipts and the exact completed frontend promotion are verified. It cannot rerun migrations, build/promote, replace containers, enable schedules or admit gateway writes. It uses a GET-only provider client and the shared lock, preserves original failure records and writes a separate exclusive recovery outcome. Readiness, boundary or frontend recheck failure stops the runtime. This is a reviewed failure recovery action, not an automatic release retry.
