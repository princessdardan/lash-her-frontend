# Source-owned provider fence coordination

This is source preparation for the existing reviewed staging release. No live
credential, deployment, provider, Redis or database was changed. The accepted
C07/network/private handoff remains an input; this component does not request it
again or add a signer, approval click, expiry permit or production operation.

## Actual control sequence

The coordinator retains its environment lock and physical migration connection.
After the real closed admission-compatible bootstrap has been built, probed and
promoted, `fenceFrontendExternalProducers` observes the original runtime bindings,
suspends native scheduling, retires exact reviewed historical deployment IDs,
disables selected staging Sanity hooks, and captures both selected CRM/shipping
principals and their actual fixed-query database PREstate. These controls do not
declare a running-effect drain.

The coordinator then commits selected historical SQL `NOLOGIN`, terminates the
selected sessions, waits for actual admitted active **and** uncertain operations
to reach zero, and closes recovery. Only then does
`reconcileFrontendExternalProducers` execute supported provider retirement and
readbacks. Square, Google, HighLevel and Chit Chats use the existing operator's
supported console action where no safe public management API exists. The same
action observes actual denial within the remaining observation budget; no new
confirmation field substitutes for denial. Square callback disable and Resend
webhook/key deletion retain their individual acknowledgements and readbacks.
HighLevel refresh is probed once, after old access denial. Lost acknowledgements
and an existing exclusive verification intent prevent automatic replay.

The independent observer reads every applicable source-owned provider component
and actual SQL role/session/admission state. It constructs retained per-surface
observations, reconciliation bytes and evidence hashes. Honest unknowns are
retained before the unchanged strict validator refuses SQL. A static list of
unsupported vendors and the previous unconditional whole-fence refusal are no
longer the execution path.

## Original runtime and physical database binding

The normalized public `historicalRuntimeBindings` identifies each selected
deployment/direct caller by `surfaceSha256`, its original `sourceCommit`, a
`configurationRecordSha256` for the **nonsecret original provenance record**,
the selected historical SQL role name/OID, and exact selected provider credential
variable references. It cannot contain secret values or secret-derived hashes.
Deployment sources must match the complete reviewed deployment inventory. SQL
roles must be among the exact selected retired roles. Arbitrary runtime variable
names, foreign provider surface IDs and duplicate credential references refuse.

The existing private runtime supplies `historicalRuntimeConfigurations` keyed by
surface hash. Each record supplies that same original source/provenance identity,
its private original `databaseUrl`, and its selected private `providerCredentials`
map. The map is privately compared to the selected retired runtime credentials;
neither values nor hashes of values are retained. Current Vercel project env
values cannot stand in for an immutable historical configuration record.

Before retirement, the source actually connects with each original selected SQL
credential using verified TLS, read-only transactions and bounded timeouts. Only
the selected staging direct host or its exact Neon pooler spelling is contacted.
The parent holds four unpredictable, temporary advisory-lock markers; the
historical connection must see all four on the same parent PID and database OID,
and must report the exact reviewed role/OID, database and server major. Matching
hostnames alone do not prove the same physical database. Markers are released;
the probe changes no business data. Missing original records remain missing
evidence. They do not cause a new credential request or invent a runtime binding.

The private supplier's selected old/replacement credential strings are pinned in
memory for that action. Substituting an arbitrary invalid string between the
preflight, retirement and independent observation refuses. Verification grants
may continue through the separately documented Google recovery flow.

## Fixed effect-capable writer predicate

`frontend-provider-fence-join.mjs` retains `rawInvocationCount: null`. It derives
zero effect-capable historical writers only when all of these actual joins hold:

- Every historical deployment/direct-caller surface matches its original
  reviewed provenance and actual physical SQL/provider capability observation.
- The source is covered by the reviewed candidate's complete admission coverage.
  This currently means the exact candidate source. Candidate coverage does not
  automatically certify C07 or another historical revision.
- Actual historical logins remain `NOLOGIN`, dedicated/unprivileged with no role
  memberships, and have zero sessions across databases.
- The actual admitted ledger has zero active and uncertain operations before
  application SQL; every selected accepted/potential provider operation has
  complete positive settled receipts.
- Complete Vercel readbacks match the reviewed inventory/retirement, native
  schedules remain disabled, and no alias job is active.

Each reconciliation retains evidence IDs for the actual capability PREstate,
physical SQL readback, provider readback, retirement receipts and ingress readback.
No caller-supplied invocation count, `complete`, `fenced` or checkbox can install
this predicate in the source-pinned release.

The currently complete selected joins are Chit Chats client/object/job receipts,
Google client/grant/Calendar/Redis receipts, and the selected Sanity callback
scope. Chit Chats acknowledged carrier states can be settled API effects while
physical delivery continues; compatible admitted polling remains separately
required. Sanity fences its operational callback/SQL capability and preserves
unrelated public/editorial API access. No unrelated frontend Mux key or public
asset/signing credential is retired.

Actual remaining gaps stay specific: HighLevel workflow history/downstream
delivery and inbound webhook completeness; Resend contact/marketing operation
reconciliation beyond the exhaustive email inventory; complete Square financial
intent and accepted-request inventory beyond the selected payment/refund rows;
and historical sources/configurations outside the positive source/capability
proof. Existing flags or credential denial do not convert those gaps into zero.
These observations do not certify the current historical staging scope or G2.

## Restoration and read-only recovery

Before opening admission, the strict closed after-promotion fence and all its
exact evidence bytes are retained. At restoration checkpoints after admission
opens, the observer independently validates those same immutable strict bytes,
rereads SQL/ingress and the old provider capability denials, and keeps current
admitted activity separate. New replacement-client shipments or current active
operations do not require the whole account to remain frozen. Current uncertainty
still refuses through the existing restoration checks. A reenabled old capability
or changed historical SQL/ingress fence refuses.

Deliberate recovery receives the actual locked read-only database client and
original receipt directory. It performs reads and bounded source reducers only;
it does not retry a deletion, refresh grant, SQL migration, credential retirement
or admission opening. Original AppUninstall and Calendar recovery receipts remain
immutable and are classified through their source-owned transition reducers.

Owned validation covers verified HTTPS provider controls, fixed Node/Python SQL
parity, canonical snapshot hashes, actual PostgreSQL 16 TLS/SCRAM and all 83
migrations, plus the coordinator's existing owned HTTP provider model. The model
does not certify the live adapter. See the
[validation record](baselines/2026-11-05-provider-fence-join/validation.json).
