# Managed Neon replacement boundary

Dardan approved source implementation on November 9, 2026 (Toronto). The approval covers the exact managed catalog boundary and preparation of a separate ACL action. The PostgreSQL 18 target is provisioned on the existing Vercel-managed Launch installation. It has one primary compute, zero connected Vercel projects and no injected environment variables. The provider SQL Editor observed the exact new `main` branch and default database. The read-only queries found no application relations, extra schemas or extra extensions. The stock empty-target verifier refuses the observed provider catalog. [Provisioning and catalog evidence](../baselines/2026-11-09-p2-neon-replacement-target.json).

The new database grants `PUBLIC` connect and temporary-table access. Neon also created two default ACL rows owned by the provider's `cloud_admin` role, which grant `neon_superuser` privileges on future tables and sequences created by that role in `public`. The only other nonzero catalog observations were their four matching dependency rows. The effective login list contains the database owner and two provider roles. PostgreSQL applies a default ACL when its owner creates an object, so the managed rows do not set privileges on objects created by the reviewed migration and frontend roles. Recheck the creator, effective login membership and exact ACL graph over the selected direct connection before relying on that inference. [PostgreSQL default privileges](https://www.postgresql.org/docs/18/sql-alterdefaultprivileges.html).

## Approved acceptance rule

Allow a dedicated managed-Neon selection for this exact project, branch, primary endpoint and database. Bind it to a reviewed, source-recorded provider baseline with the exact database and owner OIDs, the two provider login roles and attributes, the reviewed default grant owner/grantee/OIDs/privileges, and all four dependency rows. Re-read those values on the same direct TLS PostgreSQL session used by the release guard. Require every other object, extension, setting, dependency, login and prepared-transaction check to retain its existing strict predicate. Unknown, additional or missing provider rows refuse. Keep the stock verifier for unselected targets.

Check the actual memberships and role switches for the migration login and the two fixed frontend roles. Require that application SQL runs under the reviewed migration or frontend owner identity, never under a provider role. Keep provider roles and their grants intact. Independently verify the application role has only the intended privileges and no provider-role membership after preparation.

The follow-up provider read identified direct endpoint `ep-lingering-meadow-bc80gyj9.c-16.us-east-1.aws.neon.tech` and nine exact role edges. `neondb_owner` and `neon_service` both inherit `neon_superuser`. That role has explicit database connect, create and temporary privileges. The expected post-revoke effective login set still contains `cloud_admin`, `neondb_owner` and `neon_service`. The direct connection must independently prove that expectation.

## Target ACL and release steps

Prepare a separate owner-reviewed action on the selected new database to revoke `CONNECT` and `TEMPORARY` from `PUBLIC`. First confirm the physical target, current privileges, expected owner and effective login list on the direct endpoint. Recheck the result with the same target binding. The action applies to the new database only. It supplies no migration authority.

The supervised empty-target arm and reviewed release must each obtain their original host and PostgreSQL locks, verify the full selected boundary, and refuse changed runtime or provider state. Keep the old staging database, production database and both current Vercel deployments in their existing paths. The normal explicit candidate publication and release actions still apply.
