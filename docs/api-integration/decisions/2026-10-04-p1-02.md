### Separate the networking decision from the hosting decision

The add-on follows from our chosen source-IP restriction, not an inherent
requirement to use Vercel with an external API. Two proposed alternatives are:

1. Keep the frontend on Vercel and authenticate gateway calls using verified
   Vercel OIDC deployment identity, in addition to existing user/service JWT
   authorization. Verify signature, issuer, audience, expiry and exact allowed
   project/environment. Retain HTTPS, bounded request handling/rate limits and
   signed webhook exceptions. OIDC is available on all Vercel plans. This removes
   reliance on source IP for caller identity, but leaves the gateway reachable
   from the internet; it is not equivalent to a network allowlist. It needs
   boundary/abuse tests and an explicit replacement decision. Sources:
   [OIDC federation](https://vercel.com/docs/oidc),
   [own-API verification](https://vercel.com/docs/oidc/api).
2. Move the Next.js frontend and backend processes onto one VPS, expose only the
   public reverse-proxy routes and keep API/worker/metrics ports internal. Retain
   service authorization and the current internal TLS requirement until a
   replacement design is explicitly accepted. A VPS's own static public IP does
   not fix Vercel's outbound IP problem if the frontend stays on Vercel.

VPS and AWS are overlapping categories: Lightsail is an AWS VPS offering. Buying
seven separate VMs is unnecessary for seven processes; separate containers can
share one host without merging repositories or database ownership. Proposed
Docker Compose orchestration changes the deployment/failure boundary, not the
application's service contracts.
