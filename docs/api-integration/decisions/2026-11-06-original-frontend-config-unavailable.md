# P2 decision: original frontend configuration archive does not exist

Prepared November 6, 2026. Design/evidence analysis only. No resource, deployment, credential, provider, SQL, admission, schedule or policy change is authorized by this memo.

## Recommendation

Keep the existing staging P2-00 barrier unresolved. Give independent historical evidence one finite feasibility check, limited to named missing facts and supported provider records. Do not make another archive or credential request. If that check cannot establish the required original bindings and accepted-effect coverage, the practical way to continue P2 qualification is a **separate, fully isolated environment**, subject to an explicit owner decision about its target and acceptance scope. Creating that environment would not complete the old environment's P2-00 or reconcile its outstanding effects.

The current plan cannot be declared complete merely by choosing a different environment. Without an approved target/applicability change or sufficient independent historical proof, existing-scope P2-00 and its dependent deployed G2 acceptance remain blocked.

## A. Independent historical evidence: useful, but no complete recovery path is established

Vercel documents that environment edits affect new deployments and leave earlier deployments using their earlier values. Its project-environment API is a project/branch/custom-environment interface, not a documented deployment-ID configuration-history interface. Therefore, reading today's project configuration cannot reconstruct an old deployment snapshot. The deployment owner GET supplies additional metadata; the actual retained collection established key names only. No supported complete historical-value retrieval or nonsecret binding-attestation procedure has been established in this review. This is a limitation of the established evidence, not a claim that Vercel support can never recover anything. [Environment semantics](https://vercel.com/docs/environment-variables); [rotation semantics](https://vercel.com/docs/environment-variables/rotating-secrets); [project environment API](https://vercel.com/docs/rest-api/projects/retrieve-the-environment-variables-of-a-project-by-id-or-name); [deployment GET](https://vercel.com/docs/rest-api/deployments/get-a-deployment-by-id-or-url).

| Independent source | What a positive, authentic record could establish | What it cannot establish by itself |
| --- | --- | --- |
| Retained deployment owner metadata and complete original key-name catalogs | Exact deployment/project/time and source where present; source-reviewed absent-key predicates | Present-key values, selected database/account, original selector values, historical accepted effects |
| Complete provider-retained source files for the five CLI deployments | Exact bytes/tree; possibly an exhaustive match to a known Git tree and subsequent reviewed source profile | Runtime environment, direct caller configuration, provider execution history. A truncated tree or file UID list remains insufficient |
| An existing deployment-specific build/provenance record, or a provider-assisted deployment attestation | Only the exact original nonsecret target/principal/credential-version associations it actually authenticates; build-inlined constants where proven | Unrecorded runtime variables or a full configuration assembled from present-day defaults. New source consumption would need review; an operator assertion is not an existing reducer |
| Existing provider request/response, execution, webhook and SQL intent records | Particular accepted requests, immutable object/idempotency joins, terminal outcomes and outstanding work, with exact account/lifetime/page coverage | All-time completeness outside retention, deleted transient objects, lost requests without durable identities, or attribution to an unknown caller |
| Already-retained secret-version references or SQL connection/audit metadata | A specific authenticated version/principal/connection event if independently linked | Which version every deployment/direct caller used, complete original configuration, or provider effects. No AWS value retrieval is proposed |

The two deployment-file GET interfaces are documented specifically for CLI/API file deployments. They are a concrete candidate for resolving the five source identities if the provider still returns a complete tree and all required files. No such read or reconstruction ran here. Source files must be handled privately because they may contain embedded secrets; executing an old application to inspect it is not a read-only evidence procedure. [List deployment files](https://vercel.com/docs/rest-api/deployments/list-deployment-files); [file contents](https://vercel.com/docs/rest-api/deployments/get-deployment-file-contents).

Logs can resolve individual effects but must not be promoted into lifetime absence proof. Vercel runtime retention depends on plan; its audit logs are an Enterprise feature and describe account activity, not a promised full deployment credential snapshot. Resend exposes original request/response log detail. Square retains API logs for 28 days and truncates entries beyond its documented size. HighLevel webhook logs retain 30 days. None establishes that all relevant lifetime records remain available here. [Vercel runtime logs](https://vercel.com/docs/logs/runtime); [audit logs](https://vercel.com/docs/audit-log); [Resend log API](https://resend.com/changelog/logs-api); [Square API logs](https://developer.squareup.com/docs/devtools/api-logs); [HighLevel webhook logs](https://marketplace.gohighlevel.com/docs/webhook/WebhookLogsDashboard/index.html).

**Bounded feasibility result to request from a later authorized read-only step:** one coverage register, not more raw credentials. For each unresolved surface/family, name the authoritative source, exact deployment/direct caller and source binding, target/principal/version association, earliest/latest covered time, pagination/retention/deletion limitations, immutable request joins, and the specific missing requirement IDs. First establish whether the platform can supply a deployment-specific binding attestation without disclosing values. Stop a lane when the provider cannot supply the missing original association or required lifetime record. No source-only adapter should be built for evidence that does not exist. No support message or authenticated export is sent by this memo.

## B. Separate fresh P2 qualification lane

This is the preferred forward option **if A cannot close the concrete gaps and Dardan chooses a changed target scope**. It creates an additional environment; it does not recreate, delete, rotate, repoint or retire the existing staging environment. The release policy permits recreation of disposable staging only after its producers are suspended, a prerequisite not established for the old scope. [Release policy](../release-policy.md).

| Boundary | Proposed minimum isolated scope and proof before use |
| --- | --- |
| Frontend/control plane | New project and distinct test origin; no old domain reassignment. Prove old runtime and machine/control-plane credentials have no grant to the new resources. A new project inside a shared team is insufficient if an old broad token can manage it. Suppress unreviewed preview/direct-caller paths from the beginning and retain each authorized caller's original configuration provenance |
| Three operational databases | Empty independent projects/clusters and new migration/runtime roles; no old database clone, role/password reuse, PII, pending jobs, outboxes or restore. Apply complete reviewed migrations through a qualified operator path, not staging seeds/schema push. Verify TLS, exact physical targets, roles/OIDs/ACLs and current lineage under actual locks |
| Host and gateway | Distinct staging host/runtime/configuration/admission namespace, isolated from production and the accepted C07 recovery host. New exact project OIDC trust, TLS and source-bound ten-service topology; no inbound trust for old deployment/project identities |
| Google/customer auth and mail | Dedicated test clients/audiences and controlled accounts; separate applicable OAuth/Calendar resources. New signing/callback bindings and mail scope; no imports of old refresh grants, sessions, KV state or contact/automation history. A sending-only mail key is not account isolation from an old full-access key; use a separate account/team or prove an equivalent provider boundary |
| Course media | New Mux environment with its own access/signing keys, assets and webhooks, plus actual environment readback. Mux documents environment-scoped resources and tokens. Keep public/editorial media and old Course assets untouched |
| Editorial and other integrations | Separate Sanity project/project-scoped grants if needed for the full existing-site matrix; no operational PII in Sanity. Establish exact isolated test scope for any configured Square/ChitChats/CRM/Calendar integration. Otherwise explicitly omit its credentials/routes from the new original configuration only where reviewed source applicability permits. A current false flag cannot serve as historical proof |

A Neon child branch is a copy-on-write data clone, and parent roles are copied. It is not the proposed empty starting point. [Neon branches](https://neon.com/docs/manage/branches); [role copying](https://neon.com/docs/manage/roles). Mux provides a documented environment boundary; Sanity distinguishes project tokens from broader personal/organization grants. Square Sandbox is separate from production, but that does not prove separation between old and new sandbox sellers/apps. These capabilities require actual selected-scope proof before use. [Mux environments](https://www.mux.com/docs/core/mux-fundamentals); [Sanity tokens](https://www.sanity.io/docs/content-lake/http-auth); [Square Sandbox](https://developer.squareup.com/docs/devtools/sandbox/overview); [Resend key permissions](https://resend.com/changelog/new-api-key-permissions).

The isolation claim is narrower than “no old work exists”: old callers must lack access to the **new** SQL/provider/control scopes, and old callbacks must not be routed to them. Every new resource's initial state, credential provenance, ingress, schedules and first accepted effects must be recorded from creation. Future lost acknowledgments remain real uncertainty. If an old broadly scoped credential could still reach a proposed new resource, that resource is not isolated; select a stronger account boundary or keep the lane blocked.

## C. Conditions that must remain unresolved

- A deployment/direct caller has neither an authoritative complete source identity nor sufficient original configuration/binding provenance. Five retained CLI surfaces currently still have the source-identity problem.
- The exact historical SQL target/login/OID or provider tenant/app/key/grant/callback association cannot be established independently. Today's matching configuration is not historical equality.
- An applicable lost-ack/pre-intent path has no durable original request/object identity, or required logs are expired/truncated/deleted. A deleted ChitChats probe and absent current drafts are a concrete example. Revocation prevents future use; it does not settle prior accepted work.
- A provider scope is shared with production or eligible existing financial/booking recovery, and no safe independent fence can be proven. Do not revoke it globally to obtain a pass.
- A fresh lane reuses old broad control-plane access, data/roles, callback destinations or provider resources. New names or fresh keys alone do not remove old access.
- The owner does not approve a new acceptance target, or its affected G1/P2 cases cannot be qualified. The current plan remains blocked rather than waived.

These are evidence and design limits, not inferred zero counts. No source gate is weakened. Production, Phase 3/cutover, paid checkout and deferred monitoring remain excluded. Old original receipts and accepted C07 remain unchanged.
