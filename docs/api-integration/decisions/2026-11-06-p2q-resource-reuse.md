# P2Q resource reuse and shared administration

November 6, 2026 (Toronto). **APPROVED OWNER SCOPE CHANGE.** Dardan instructed: “Remove the requirement for P2Q to be completely separate. This is an unnecessary requirement given that this project is maintained entirely by a single developer.” This decision takes precedence over the complete-separation/new-only requirements in the earlier [isolated-lane plan](2026-11-06-isolated-p2-qualification-lane.md) and its downstream proposals. The earlier decision and original source/evidence records remain historical, not current separation requirements.

## Removed requirements

- No separate human administrator, provider account/team/organization, administrative principal, credential set, MFA or recovery channel is required solely for P2Q.
- No proof that every historical broad administrative credential or recovery path is unable to reach P2Q is required. Dardan may administer staging and production from the same account.
- No mandatory new Google project, Vercel team/project, standalone VM, independent root database project, separately controlled DNS zone or all-new provider scope is required. Existing staging resources may be reused; sharing a provider administrative scope or host does not itself disqualify the target.
- Reused resources do not require original creation-time, original credential-download custody, complete control history from birth, zero containers, zero prior lineage or a first-use/allocation authority factory merely to qualify as P2Q resources. Review their actual current identity, configuration, permissions and state instead.
- Do not require a new Google account or reject the identified staging account because it administered historical staging. Its existing project and appropriately configured existing OAuth clients may be used. Creating additional clients or changing redirects, if needed, remains an ordinary separately reviewed provider change.

## Current execution path

P2Q/G2-Q names the certification claim, not a requirement for a physically new environment or a new target-profile kind. Prefer the supported existing-staging release/upgrade path when reusing the current target. Exact selected IDs and configuration still bind the release; register genuinely different targets through the reviewed source process rather than guessing IDs or bypassing validation. A reused nonempty database uses its supported lineage/upgrade path and is not called virgin or empty.

The ordinary frontend and both APIs already support existing staging without an independent-account check. The optional Google project-creation capture and virgin host/database collectors are not prerequisites for this path. Their creation-only/empty-target assertions remain truthful within those optional tools; do not fabricate a CREATE receipt for an existing project, reinterpret a reconciliation call as adoption, or relax an empty-database assertion to accept existing data. The incomplete Google guardian work is stopped, preserved outside integration and not required for resource reuse.

Profiled apply/context propagation refusals are separate source limitations. This decision does not bypass them or convert an observation into release authority. Use only a supported reviewed release path for the selected target. Likewise, provider retirement tools that currently assume an account-wide scope need resource-specific attribution before use against a shared account; do not retire unrelated production webhooks, keys or grants to force a staging pass.

## Requirements retained

- Preserve production and existing data. This decision does not authorize deployment onto production, production activation, destructive resets, or importing production data. Keep environment-specific runtime targets/origins and the required customer/admin/service authorization boundaries.
- Verify the current selected source/artifacts, target IDs, runtime bindings, required permissions, TLS, database roles/OIDs, complete migration lineage and schema. Keep ordinary least privilege, private credential handling and reviewed target guards.
- Keep the single-operator release procedure, physical host/database locks, whole-operation admission, actual producer inventory/drain, supported failure recovery and refusal of unresolved active/uncertain operations. Do not infer a successful old effect, historical fencing, migration or deployment from this owner policy decision.
- Preserve accepted recovery-only G1; requalify affected checks for the actual selected release. Complete the required S01–S17/P2Q evidence, paid-grant S10 and real Google/Resend/Mux, authoring, learning, lifecycle and export-expiry certification.
- Preserve the accepted P2Q/G2-Q scope boundaries: old P2-00 and previously excluded retained-history/functional claims remain separately OPEN, without being represented as recovered or passed. Phase3, paid checkout, Community member features, production activation and deferred monitoring remain excluded.
- Resource allocation, spending, provider/credential changes, candidate publication and live release still require their existing concrete owner actions. Removing complete separation is not authorization to perform them.

## Application to existing evidence

Separate-account/new-only recommendations in the allocation, Google-client capture, Mux and first-install proposals are optional alternatives, not eligibility gates. Their factual observations, hashes, source checks, failures and original receipts remain unchanged. An old observation is not fresh runtime evidence, and an existing staging resource is not automatically certified merely because reuse is now allowed.

The next setup work identifies and verifies the selected existing staging resources and their current required configuration. Do not request a new independent account or a historical configuration archive solely to establish administrative disjointness.
