# Existing-principal reach: source-only counterfactual analysis

November 6, 2026. No credential, account, Console, IAM simulator or provider-control request was executed. This tests the proposed design against documented authorization rules and the exact local policy source, not against unknown live token values. Actual old-key scope, validity and grants remain UNKNOWN. No historical token is revoked or presumed revoked.

**Same-account new resources do not establish strict isolation.** The selected prerequisite is a new independently controlled administrative principal and a resource/account boundary that excludes old principals, inherited administration, integration and recovery reach. Dardan remains the same trusted sole human; that does not make a pre-existing broad credential safe. A new credential owned by that same old administrative principal generally does not remove the old credential's rights.

## Exact offline AWS counterexample

The read-only local check in `control-reach-analysis.json` parses the original JSON rather than relying on names. It verifies:

- the source operation statement is `Allow`, includes all four host-control/access-material actions, and uses an account/region `Instance/*` ARN;
- its tag predicates include `lash-her` and `staging`;
- the proposed reference host template emits those same tags.

Thus a same-account new instance carrying the template tags satisfies the **shown statement's resource/tag selection**, provided the old role session is otherwise effective. No resource was created, no actual token was tested, and no overall live IAM decision is claimed. This is sufficient to reject a planning assumption that a new host name/key automatically isolates it.

For other providers the cited official scope/default rules supply counterfactual reach, not a live inventory. The eventual source observer must verify the actual selected original creation principal, complete relevant grants/ancestry/integrations and custody history. A current successful new-key request would prove only that key works; a failed old-key request could be due to wrong credentials/target and would not replace the complete proof. If the provider cannot support the required bounded evidence, keep the resource ineligible rather than inventing a universal token inventory, owner assertion, revocation, or account-isolation pass.
