# P2Q resource allocation proposal

Planning only, researched November 6, 2026. No resource, account, credential, DNS, billing, provider, SQL, deployment or publication action was performed. All allocated IDs, domain availability, account eligibility, private prices and actual grants remain UNKNOWN. The approved decision authorizes revised P2Q/G2-Q scope and source implementation; it does not authorize allocation or spending.

## Recommendation

Use one independent administrative boundary per selected provider, one separate Lightsail host, three genuinely new Neon root projects, one Vercel frontend project, and new Google, Resend, Sanity and Course-only Mux scopes. Start with the low tiers below. Reuse reviewed source, public artifact infrastructure and the ten-service topology; do not reuse old databases, machines, account-wide tokens, SSH keys, provider secrets, OAuth grants, callbacks or runtime configuration.

The known full-month fixed subtotal is **US$47.10** for the proposed 4 GB host, one Vercel Pro seat, four Secrets Manager records, one KMS key and one Route 53 zone. A standard `.com` registration adds **US$15 upfront per year** at current published pricing. This is a partial estimate, not a ceiling or a complete invoice: usage, tax/FX, unknown account/mailbox requirements and any plan changes are excluded. It does not establish that the operator's US$50 target is met. No private billing access or hard-cap admission gate is proposed. The reproducible arithmetic and exclusions are in `cost-model.json`.

There is no authentic production creation/control/first-use authority factory yet. The proposal is concrete enough to select costs and boundaries, but **not executable through the current first-install CLI**. The collector proves only scoped core-catalog counts and host facts, explicitly not complete database emptiness or first-use authority. Allocate only after the corresponding source capture path and concrete resource/spend action are reviewed; keep unsupported proof obligations unresolved.

The [explicit existing-principal reach matrix](control-reach-analysis.md) covers same-account/team/org counterexamples, creator defaults and narrow-token distinctions. Its offline AWS statement-selection test confirms that the existing tag/wildcard role source covers a same-account host with the reference template tags; no live effective-IAM or credential decision is claimed. Independent owner-auth/recovery setup remains an exact prerequisite, not an executable pass.

## Creation order and exact hold points

These are future actions, not commands to execute now. Each mutation requires a durable exclusive source intent before dispatch; retain ACK or uncertainty once, never blindly repeat a create/key POST after timeout.

1. **Freeze the blueprint and implement capture first.** Hash the nonsecret selected plan; keep source/current profiles unchanged. Fix resource types, proposed names, source adapters, allowlisted control endpoints, private custody recipients and no-delivery transitions. Source must distinguish account/control records from credentials. No JSON `created`, `fresh`, `ownerConfirmed` or empty inventory may issue authority.
2. **Establish independent control/recovery principals.** After resource authorization, create/verify the selected provider boundaries and privately controlled recovery channel. Capture actual immutable account/org/principal IDs, membership/integration/API-key scope and inherited roles. Old broad personal credentials must not acquire reach through the new principal/team membership. Where the provider cannot expose sufficient grants or an authenticated control capture, retain the missing requirement; do not spend on downstream resources as though isolation were proved.
3. **Prepare custody and namespace.** In the new AWS account, source-reviewed IaC creates the one KMS key/four private records; no old-account grants. Register the chosen available domain only after its exact quote/name is accepted. Capture registration request/ACK/registrar identity, domain lock/recovery configuration and exact zone authority; no app DNS or callback activation yet. Domain purchase is annual and potentially nonrefundable. New account/paid Vercel enrollment may create billing commitments.
4. **Create three new Neon root projects.** Supported `POST /api/v2/projects` takes organization, region and major. The creation response can include a password/connection URI: route it directly into private custody, never agent/common logs or credential-derived public hashes. Wait for returned operations; read back project/root branch/direct endpoint/role identity and absence of parent/import. No Neon Auth/Functions/storage integrations or Git previews are enabled. No application credential is distributed. [Creation contract](https://neon.com/docs/reference/api/projects/create-project).
5. **Allocate the empty host via a NEW CloudFormation stack.** Use the source template's one-host/firewall pattern with separately reviewed new-account scope and new SSH public key. Read back stack/resource state and static-address attachment. Hold before SSH/bootstrap until authenticated host-key/instance binding exists. Existing fixed old-host SSH helpers cannot select this host. `GetInstanceAccessDetails` contains temporary access material and is not a harmless public-host-key read; a safe supported capture procedure remains unimplemented.
6. **Create inert SaaS resources.** One Vercel project without Git/automatic deployment/app secrets; one Google project and two exact-origin clients through supported Console steps; one Resend sender-domain record without sending; one public Sanity dataset without imports/hooks; one Mux environment without assets/uploads/hooks. Account/project creation itself is recorded, but no writer delivery is inferred absent just from current lists. [Vercel project creation](https://vercel.com/docs/rest-api/projects/create-a-new-project), [Google clients](https://developers.google.com/workspace/guides/create-credentials), [Sanity projects](https://www.sanity.io/docs/http-reference/projects-api), [Mux environment concepts](https://www.mux.com/docs/core/mux-fundamentals).
7. **Join real IDs to the profile without rewriting creation history.** Root registers the actual allocated profile only after genuine IDs and control evidence exist. Append a join referencing the unchanged blueprint/create/control/custody records. Rebuild/source-qualify affected exact artifacts and profile consumers. No placeholder profile or stamp on old receipts.
8. **Run the complete first-use boundary under actual locks.** Fresh host/physical-PG/role/target/custody/control proof must be collected before migration. The present collector's core-catalog observation is insufficient; missing catalogs/settings/memberships and complete target/creation proof must be supplied by the authentic source factory. Ordinary absent-prior-gateway refusal is not weakened. Prepare roles/admission/migrations only through the approved existing typed primitives, never an ad hoc DDL executor.
9. **Deliver only declared writer capabilities and then enable ingress deliberately.** Record exact original environment key catalog and private version/provenance per deployment/direct caller before handing over values. Use runtime dynamic references/`asm-exec` for AWS-held values, not agent secret reads. Operator-only full control keys do not enter frontend/host CI configuration. Keep native/business schedules and admissions at the reviewed closed stage; qualify the actual OIDC/TLS/ten-service/G1 boundary before account traffic.
10. **Create selected callback capabilities under a live reviewed stage.** Mux webhook creation enables it immediately and returns the signing secret once; it is not inert setup. Create only after the actual closed/authorized destination, private capture and admission/callback persistence procedure exist. [Mux webhook contract](https://www.mux.com/docs/core/manage-webhooks). 11. **Perform actual S01–S17 in the accepted claim.** Use ordinary owner/customer/staff UI/API entrypoints; no SQL seeds, ad hoc JWTs, paid-course checkout, real charges/refunds/postage or ordinary marketing sends. 12. **Teardown is a separately reviewed resource action.** Close/drain actual writers/ingress and retain exact evidence/private recovery inputs before deleting anything. Stopping a Lightsail VM does not stop billing; deleting it destroys its root disk, and the static address/secret/key/domain/subscriptions can remain. No automatic expiry or blanket account deletion is proposed. Preserve the old lane throughout.

## Reuse and excluded allocations

Safe reuse is limited to reviewed code/locked dependencies, public editorial bytes with publication rights, sole-human operator ownership, existing trusted local tooling and read-only immutable artifact distribution. Reuse existing public repositories/manual candidate publication; do not introduce a new GitHub Environment, signer or approval ledger. Exact new candidate/source/configuration applicability must still be qualified.

Do not reuse old runtime databases/branches/snapshots, SSH trust or private keys, deployment/private environment files, provider tokens/OAuth grants, callback secrets/URLs, machine access roles, native project controls or private retained application data. Do not copy old Sanity/Studio Mux private operational state. Public Mux/Sanity capability is not retired by this plan.

No new load balancer, NAT, Kubernetes, monitoring stack, managed AWS database, Community media feature or paid online-course checkout is selected. Square, ChitChats, HighLevel/CRM and Calendar remain unconfigured for the accepted boundary-only S17 subcases. That is not a functional-compatibility pass. KV is conditional: the legacy `src/lib/courses/rate-limit.ts` requires a real KV URL/token for legacy signup; the new P2 learner enrollment is a separate API path and public inquiry/training actions use the reviewed local/SQL path. Select a new independent KV only if the exact required scenario reaches that legacy path; otherwise retain explicit unconfigured behavior. This proposal does not silently declare all legacy signup subcases passed.

## Factual blockers before allocation/use

- Exact independent provider principals, recovery channels, grants/integrations and policies have not been observed. A new team/org label or owner statement proves none of them. SaaS Console/control capture and the positive authority factory are not implemented.
- The proposed domain may be unavailable; exact registration eligibility/quote, DNS rights and certificate establishment remain unknown. No old-domain credential change is authorized.
- Fresh host key binding, actual bundle/AZ/new-account quotas, and measured ten-service capacity remain unqualified. The $44 8 GB alternative is a separate size/cost choice, not an automatic escalation.
- Source-fixed selectors/roles/new-target transports and the complete first-install composition still need integrated qualification. Actual profile IDs and OIDs cannot be filled from labels. The current observation-only collector cannot fill the missing authority.
- Required real provider operations may lack complete control/history interfaces. In particular ordinary Google OAuth client birth/admin evidence and Mux organization/environment control capture need supported Console/source adapters; no generic public API is invented here. Resend list metadata cannot reconstruct one-time token permission/custody. Missing proof refuses.
- Even a correctly allocated lane does not supply controlled Mux duplicate/reordering/lost-ACK evidence automatically. The reviewed Mux procedure documents absent public redelivery/history APIs; unsupported S05 steps remain OPEN until a concrete supported procedure exists. Account emptiness, age, screenshots or an operator zero assertion are not a substitute.
- Real consenting owner/non-editor/customer participants, inbox access, selected public editorial content, exact live no-charge grant procedure, device/browser evidence and the 24-hour window must be arranged. No contact was made and no real participant address is included here.
