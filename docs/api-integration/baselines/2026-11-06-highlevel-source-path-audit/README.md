# HighLevel historical source-path audit

The frozen conservative subset contains **35 deployment surfaces at 25 exact revisions**. Source inspection separates 12 surfaces without a HighLevel integration, 21 using the C07 location-OAuth credential boundary, and two using an agency-token exchange variant. These are candidates for a bounded source-policy extension, not runtime exclusions or release evidence. Matching outbound credential boundaries does not prove that callback, OAuth-state or queue SQL writes are unavailable. The current profiles still mark all eight HighLevel families reachable and do not reuse their credential predicates.

This audit changes no profile, selector, provider reducer, runtime configuration or admission state. It reads Git objects and existing public evidence only. It does not establish original configuration, provider account identity, SQL applicability, old accepted-effect completeness or credential retirement. The frozen 81-surface register remains unchanged; neither its 17 unprofiled nor its five missing-source surfaces are excluded. Later exact aliases are outside these counts.

## Credential and alternate-store boundaries

The 15 integration revisions use a source-owned HTTP client, not a HighLevel SDK. Its default token reader is `accessToken()` in `src/lib/highlevel/oauth.ts`. All 15 pin identical `pg` 8.20.0, `drizzle-orm` 0.45.2 and `@upstash/redis` 1.38.0 identities. SDK equality alone is not a capability proof.

| Family / path | Source-required path | Consequence for the next reviewed absence predicate |
| --- | --- | --- |
| Contacts, workflows, tasks, opportunities, conversations and messages | Default HTTP client obtains a token from `highlevel_connections` through `getPrivateDb()` and decrypts it with `HIGHLEVEL_CREDENTIAL_ENCRYPTION_KEY`. The application SQL reader uses only `DATABASE_URL`. Refresh still uses the same stored grant and encryption boundary. | For the audited deployment/default-client paths, an absent original `DATABASE_URL` or encryption-key name can block this credential path. Missing OAuth client ID/secret alone does **not** block an unexpired stored access token. Present empty/masked values are not absence. |

## Whole-operation order and SQL-only writers

The exact body/line anchors in `audit.json.operationGateAudit` bind the following order to actual Git blobs. The location-OAuth body applies to all 21 location-group surfaces; the agency body applies to the other two. The callback route, webhook handler/persistence, application DB client and pool are byte-identical across all 23 integration surfaces.

| Operation | Actual order before and after the first SQL write | What key absence does **not** prove |
| --- | --- | --- |
| Location `createInstallation` | Validate `locationId()` → generate state → **INSERT OAuth state through `DATABASE_URL`** → read client ID and redirect URI to construct authorization URL. | Missing client ID, client secret or encryption key does not exclude the state INSERT. A failure while constructing the URL can follow a committed state write. |
| Agency `createInstallation` | Validate location → construct authorization URL (client ID, redirect URI, app version, and company ID when agency mode is selected) → **INSERT OAuth state**. | Client secret and encryption key are not prerequisites to this write. The agency flag is a branch selector, not a generic operation-off proof. |
| Either installation callback | Admin permission check → validate state/code syntax → **DELETE/claim matching unexpired SQL OAuth state** → read client credentials and POST token exchange → validate provider response/location → encrypt → UPSERT connection → successful admin audit. | No HighLevel environment-key lookup precedes the state DELETE inside `completeInstallation`. Even absence of all client/location/encryption keys cannot erase a valid pre-existing state claim when SQL and admin authorization are available. Missing encryption key can fail only after provider token acceptance. |
| Signed webhook | Presence-check location key → bounded body → verify with the **built-in provider public key** → parse/match location/event → SQL transaction → **INSERT receipt first** → optional uninstall connection revocation or contact/consent/outbox updates. | Client ID, client secret, encryption key and outbound switches are not webhook prerequisites. An event that causes no contact update can still persist its receipt. There is no separate environment webhook secret whose absence disables this route. |
| Local enqueue / consent / retention | Source caller obtains the application DB or transaction → `enqueueCrmEvent`/`recordSmsChoice` writes; retention deletes states/receipts/jobs, imports expiry work and deletes expired consent. | These SQL operations have no HighLevel credential prerequisite. False outbound flags or absence of provider credentials do not disable them. Source forms, checkout/order/enrollment/consent/email paths and retention callers remain SQL-capable independently. |
| Paused worker / admin resolution | Worker may query existing contacts and cancel known journeys before returning for disabled new sync. Admin effect resolution updates/deletes pending effect rows using the authorized DB. | A pause is not whole-operation silence, and an admin “absent” choice is not proof that provider execution was absent. |

Consequently the source gate for an outbound provider family must not be copied into a callback or whole private-SQL exclusion. A legitimate release still needs the independent physical SQL-role/session/ingress fence and reconciliation of accepted or uncertain pre-fence operations. Current empty SQL tables alone cannot prove that earlier state claims, receipts or effects never existed. This audit adds no substitute for those controls.

The deployed application DB chain is `getPrivateDb()` → cached pool → `createPrivateDbPoolConfig(getCheckoutDatabaseUrl())` → **`process.env.DATABASE_URL` only**. No fallback to `STAGING_DATABASE_URL`, `TEST_DATABASE_URL`, backup URL, Redis, a secret reference, or a provider credential store occurs in that chain. SQL-stored HighLevel credentials are encrypted in `highlevel_connections`; neither their presence nor their absence changes the fact that callback/state/queue writes can occur before token decryption. All four source-wide SQL keys still require their existing original-caller provenance and physical observations where configured.

Direct/manual callers have a separate environment and entrypoint identity. The supported backfill/config-check scripts import the same application DB chain; their own resolved original configuration must be bound. A different caller can pass an existing transaction or injected client into exported helpers, and the agency revision exports `exchange` itself. Such an arbitrary caller is not covered by a deployment's missing keys or by a peer's catalog. Unsupported entrypoints, untracked dotenv files, alternate SQL clients and missing original invocation provenance remain unknown. No new direct-caller approval is created by this audit.

## Configured effects remain unresolved

The source permits direct contact updates/deletion and workflow removal while new sync/marketing work is paused. Privacy deletion can erase provider IDs and effect payloads; retention can delete old receipt/job rows. Workflow enrollment acknowledgment is distinct from downstream workflow execution, conversations and messages. Complete current SQL or provider lists do not retrospectively establish those missing outcomes.

The four store/sync versions and two retention versions share the audited credential boundary but differ in conversion, source-removal, consent, historical-job and follow-up behavior. `6e0e3d41` also adds course-signup notes and source-scoped backfill. A configured history reducer must join the exact originating source intent and provider outcome; these changes cannot be erased by a common library/SDK fingerprint. Existing admin `confirmed`/`absent` form choices and textual evidence references are not a machine-verifiable accepted-request completeness reducer.

The next bounded implementation should therefore be **source-policy qualification first**: exact-revision absence facts for the 12 integration-absent surfaces, then pinned provider-only outbound credential gates for the 21 location-OAuth surfaces while retaining the independent SQL-only operation requirements, and a separate agency/caller audit for the remaining two. Only positively configured, source-applicable scopes that survive that process should select further provider-history work. Every resulting runtime decision still requires the existing source-owned original configuration/SQL/effect contradiction checks. No step here authorizes public Mux/Sanity retirement, provider mutation or production controls.

## Reproduction and limits

The audit pins frontend source `caea30f6297a0da0b441c20cc9598ab1e798e192` and the earlier frozen register by hash. `verifiedSourceRequirements(repository, exactRevision)` was invoked for each of the 25 revisions; selected blobs were then read using `git --no-replace-objects cat-file --batch`. Core/credential variants were compared by actual blob identity; differences in OAuth/config/store/sync/retention/manual callers were inspected. The recorded import scan is supporting navigation, not a completeness assertion. Absence review also inspected the inventory's direct network sites: other-provider clients, same-site browser requests, allowlisted Chit Chats label reads, Strapi migration reads and the fixed purchasability GET. The Strapi/manual readers do not become general approved direct callers.

No API, provider, catalog, private-value or SQL read was performed. The JSON is evidence of source facts only and is deliberately not accepted by runtime closure APIs.
