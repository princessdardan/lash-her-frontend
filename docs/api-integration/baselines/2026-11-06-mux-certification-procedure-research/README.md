# Mux staging media certification procedure research

**The normal Course media flow has supported Mux operations. Forced duplicate, reordered and lost-acknowledgment cases are not all available as documented Mux account controls.** This is a researched plan, not a completed S05 test or permission to operate staging. No account, resource, browser, database, credential, webhook, configuration or worker action ran. Only local exact-source inspection and unauthenticated official documentation reads occurred.

Scope is the Course-managed P2 media flow at frontend `9480cd91b2805e2a0ab85fa2ad2f56afa2d12a8d` and Course `a447bfde20299e12afab68a3331b3792ddd07598`. [Source hashes and anchors](source-map.json) bind the findings. The source uses `@mux/mux-node` 14.0.1. No SDK upgrade is proposed. Studio, Sanity/imported media, `src/components/courses/course-video.tsx`, public media and Phase 3 remain outside this procedure. The actual learner surface is `src/components/learning/authorized-video.tsx`.

## Provider facts and limits

Mux's [webhook guide](https://www.mux.com/docs/core/listen-for-webhooks) documents environment-scoped delivery, retries after non-2xx for up to 24 hours, a five-second attempt timeout, and possible duplicate messages even after 2xx. It does not promise an exact retry schedule or a controlled delivery order. Its CLI listener/replay uses a separate local-development signing context and offers no delivery guarantees. CLI replay/trigger is not original staging-provider delivery and is excluded here.

[Signature verification](https://www.mux.com/docs/core/verify-webhook-signatures) binds the raw body and timestamp to the endpoint's signing secret; the documented SDK tolerance is five minutes. Never replay captured signatures, re-sign callbacks, replace the endpoint secret, relax timestamp checks or substitute a synthetic event. A real retry must pass the unchanged deployed Course verifier.

The frozen [official OpenAPI](https://www.mux.com/api-spec.json) has 157 paths and no event-history, delivery-redelivery, retry or replay operation. Its system webhook operations configure destinations; they are not event-delivery APIs. The [official SDK API inventory](https://raw.githubusercontent.com/muxinc/mux-node-sdk/main/api.md) is consistent with that distinction. This bounds the inspected public contract; it does not establish that an undocumented account UI cannot have another feature.

The [webhook reference](https://www.mux.com/docs/webhook-reference) exposes event/environment/object identity and attempt metadata such as attempt ID, time and response status. That schema does not supply a callable history endpoint, complete export, retention guarantee or Dashboard redelivery procedure. Do not infer those capabilities or infer zero history from an empty screen. The account Dashboard was not opened. If an authorized future operator sees event/attempt records, retain their actual environment/event/attempt/time/status joins privately and export only opaque metadata. An absent or unverified history/retry control remains UNKNOWN.

| Waiting upload cancellation | [PUT `/video/v1/uploads/{UPLOAD_ID}/cancel`](https://www.mux.com/docs/api-reference/video/direct-uploads/cancel-direct-upload) | Documented only while `waiting`. Mux assets' media content is immutable after creation; [the asset contract](https://www.mux.com/api-spec.json) distinguishes creating another asset from editing the original. Course replacement therefore needs **one dedicated lesson lineage with attempts A and B and distinct provider assets**. A literal one-attempt/one-asset limit cannot cover replacement or retry. Each extra failed/timeout attempt must be explicitly included in that test lineage, not silently adopted from existing media.

The [caption guide](https://www.mux.com/docs/guides/add-subtitles-to-your-videos) supports SRT/WebVTT and delivery in the HLS stream. Verify actual caption readiness and rendered cue content, not merely successful asset processing. A new replacement asset does not imply that the old asset's caption tracks were copied.

## Closed future execution sequence

These are operations for the already authorized certification stage after Dardan starts the reviewed staging release. They do not execute from this document or add another approval click.

1. **Bind the fixture.** Select one dedicated staging Course/lesson and its actual course revision. Bind candidate, frontend/Course source, running container/image/config identities, Mux environment and the actual Course attempt/provider IDs as they become available. Verify `managed_by_course=true`, exact environment and `lash-her-course:<environment>:<attempt UUID>` ownership using the existing private operator evidence. Do not substitute an old Studio/imported asset. Record the initial current/latest generation and actual worker enabled/cleanup state without changing configuration.
2. **Upload A through Course authoring.** Course must be draft; send the observed revision/current ID. Upload a small, owned, non-sensitive video through the actual UI. Save only opaque attempt/upload/asset identifiers and fixture-file hash. Observe status through UI and the authoritative Course refresh/worker path until an actual ready signed asset is recorded. No bounded wait becomes proof of readiness; unresolved state stays OPEN.
3. **Add, remove and replace A's caption track.** Use two reviewed public HTTPS fixture files with known different cues. Add through the form, require a ready track, remove that exact track through the form, then explicitly add the replacement with the latest course revision. Observe actual provider track IDs/status and absence/presence of the intended tracks. Keep raw source URLs and labels out of common receipts. A timeout or unknown response means refresh/reconcile the existing intent before another create/delete.
4. **Prove an entitled learner baseline.** Publish through the existing authoring gates, using the dedicated active account/enrollment/grant and unarchived lesson. Use the actual academy player to prove video, thumbnail, selected caption cues and renewal. Keep bearer/stream URLs and tokens private. Upload/caption edits require draft; learner issuance requires published content, so do not promise fresh learner playback while the replacement is being authored in draft. Existing issued tokens retain their actual expiry.
5. **Replace with B.** Return the dedicated course to draft, re-read revision/current A, and use Upload replacement. Record B's new generation and provider identities. Require current A to remain selected until authoritative reconciliation makes newest B ready; no event alone can promote it. Publish only after existing gates pass and verify actual learner playback for B. Retain A/B identity joins for stale-event observations.
6. **Observe recovery without replay.** Separate an actual scheduled worker iteration from a manual Refresh: UI refresh proves only on-demand reconciliation. Worker certification needs the already reviewed enabled process, exact source/runtime binding, a due attempt's actual claim/observation and safe status evidence. Global due/uncertain metrics alone do not prove this attempt ran. Do not enable a worker/cleanup flag, alter leases/backoff/timestamps, or replay provider mutations to manufacture a pass.
7. **Run only explicitly inventoried negative branches below.** Keep each branch's initial/final current, latest, generation, error, caption and ownership observations. Missing provider effect, missing delivery identity, equal/ambiguous event timestamps or expired observation budget keeps that case OPEN. A passed normal upload cannot stand in for a transport fault.
8. **Close the fixture observation.** Record final state and unresolved outcomes. Existing cleanup can delete only an eligible superseded managed object after actual token expiry/reference fences. Do not create a retention policy, shorten token lifetime, delete an unmanaged/current object or change provider webhook configuration for certification.

## Minimal observation seam; no new provider control

Managed callbacks only wake recovery; authoritative provider reads determine state. Current `wakeWebhook` does not store event history and current SDK normalization drops event creation time. Current/latest UI snapshots therefore cannot establish delivery order by themselves.

The smallest proposed receipt can be emitted at the **existing gateway after the complete upstream 200**: bind incoming opaque event identity/type/creation time to the exact closed Course response and actual before/after managed-row proof. Course's legacy fallback updates only `managed_by_course=false`; with the pinned source it cannot return the same prebound managed primary-key row. This source/DB/response join can distinguish a managed wake without adding a Course endpoint or changing signature verification. Any 200, a 204, an unmatched row, an invalid body, a stale source/process or an unknown generation is insufficient. [The proposed closed receipt schema](observer-receipt.schema.json) is documentation, not an implemented verifier or a caller-supplied completion certificate.

A future scoped collector may project only selected `video_assets` IDs, lesson/generation, ownership/environment, provider IDs, current/status/error, recovery attempt/lease timing, superseded/deleted timestamps and actual token expiry; captions project only ID/language/status/closed-captions. Never read/export `raw_payload`, source/upload/stream URLs, raw request/response headers, signatures, secrets, token bodies, titles, contact data or arbitrary application rows. Existing Course Refresh is not this read-only projection.

The driver owner has proposed a root-private, single-match, expiring transport lease on the existing gateway, with no public activation endpoint. Its Mux variant would prebind the known managed attempt/environment/parent object/generation and fixed event type, then latch the previously unknowable event ID only after a verified matching managed 200; a subsequent provider retry must join that same ID. It could drop the returned ACK, not alter/sign the callback. A lost-ACK claim requires inspecting the complete bounded upstream response before sending any downstream status, headers or body; closing after Mux already received 200 is insufficient. Implementation, source qualification and live use are separate from this research; no fault file, proxy or gateway setting was created here. It cannot guarantee reordering, force a provider retry deadline or prove an outbound Mux API lost reply.
