# Product-stock sweep recovery admission

Status: disabled-by-default P2-00 source component. Pending frontend SQL, live admission and all six rollout capabilities remain disabled. P2-00 remains incomplete.

The GET export at `/api/cron/product-stock-reservations` authenticates before acquiring an independent recovery entry. That entry precedes Square configuration and candidate selection, and covers every awaited provider lookup, row-locked stock release, order/obligation cancellation and shipment abandonment. Closing new work leaves recovery independent; closing recovery refuses a new sweep while admitted work stays accounted for through final transaction cleanup. Business reservation expiry does not drain admission.

Caught provider-verification failures and per-order release failures mark operation-local uncertainty before existing fallback/logging. A four-page Square scan with a remaining cursor, silently filtered malformed listing rows, or unknown matching payment status cannot establish a complete provider observation. Missing stock/release-movement/order/obligation/shipment update receipts cannot clear a success-shaped result. Explicit captured/authorized provider verdicts and ordinary concurrent-state skips remain successful skips. Ledger socket/settlement loss and partial failure summaries also refuse completion. Enforced refusal/uncertainty returns sanitized `503`, `Cache-Control: no-store` and `Retry-After: 30`.

Admission-off behavior preserves existing `200` result counters, thrown errors, bounded provider lookup and best-effort cancellation after provider verification failure. Existing reservation/stock movement identity and cancellation safeguards remain unchanged. No new retry, provider mutation or stock-release replay is introduced. The shared Square listing filter and stock release helper only add uncertainty observations; outside an admitted context those markers are no-ops. Optional candidate-list/release dependencies support controlled loop tests; production defaults retain the existing queries and transactional release.

The [validation record](baselines/2026-11-05-p2-00-stock-sweep/validation.json), inventories, classification and effect audit bind this component to its source. Controlled tests cover authentication, closed admission, independent recovery, closure during query/provider/release stages, later-order processing after errors, undefined failures, empty/skip/off behavior, truncated/malformed/unknown Square observations, missing stock and release-movement receipts and lost acknowledgements. The owned fixture extends the actual exported-route, loopback HTTP, verified TLS ledger and migrated business-database checks with nonempty stock release/cancellation, exact provider-window/location requests, durable stock/order/obligation/shipment receipts, refusal during blocked cleanup and actual ledger-backend death. A review regression suppresses a real pending-shipment update and requires an uncertain entry and retryable `503`; an order with no shipment still completes successfully. Expected shipment rows are locked and matched to abandonment receipts inside the cleanup transaction. Unresolved operations prevent drain/restoration until all HTTP work finishes and the fixture owner deliberately reconciles hashed business outcomes.

These are component checks using intercepted Square responses, synthetic rows/producer identities and a test HTTP bridge. They do not qualify a deployed Next.js server/native scheduler, real provider observation/drain, every independent caller or historical deployment. Direct sweep/helper callers do not acquire admission from this cron boundary. Exact-head CI remains required. Remaining workers/writers, actual producer/provider inventory, historical fencing/bootstrap and the parent release/restoration coordinator remain open. No live database/provider/credential/scheduler mutation or admission/pending-SQL enablement is included.
