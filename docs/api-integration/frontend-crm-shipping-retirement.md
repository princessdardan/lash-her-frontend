# HighLevel and Chit Chats credential and effect observations

This source-only host component does not enable admission, change provider settings, retrieve secrets, write business data, cancel shipments or marketing journeys, or authorize traffic. `ops/platform/host/frontend_crm_shipping_retirement.py` is callable only through the source-pinned host worker. The provider coordinator owns its integration, private credential delivery, runtime binding probes, database bridge, source joins and final decision. Existing booking, commerce, financial and marketing retention behavior remains unchanged.

The component constrains Chit Chats requests to `https://staging.chitchats.com` and one reviewed client ID. HighLevel requests use `https://services.leadconnectorhq.com`, one reviewed staging location/company pair and API `Version: v3`; the known production location is refused. Provider tokens remain in private process memory. Binding hashes identify nonsecret credential provenance records, not token values. No ambient credentials, URL overrides, proxies or redirects are accepted. Failures retain fixed error codes without response bodies, URLs, recipient details, message bodies or credentials.

The reviewed record contains `environment: staging`, `credentialKind`, `sourceBindingSha256`, `databaseSnapshotSha256`, `retiredCredentialBindingSha256` and `replacementCredentialBindingSha256`. Chit Chats adds `clientId` and the sorted complete `expectedProviderShipmentIds`. HighLevel adds `locationId`, `companyId`, sorted complete `expectedProviderContactIds` and `expectedWorkflowIds`; a private integration identifies `retiredIntegrationId`, while an OAuth installation identifies `appId` and `oauthClientId`. The coordinator must bind these records to the exact selected historical and replacement producers. These fields cannot establish that an agency credential or shared provider account is dedicated to staging; any unproved or shared scope remains unresolved. This module performs no credential deletion, so it cannot inadvertently retire an independent production/shared principal.

Before the existing trusted operator's supported console action, `suspend` reads both old and replacement principals, verifies equal selected inventories and writes an exclusive `*-retirement-before.json` receipt. This is a read-only observation. For Chit Chats the operator deletes the selected token under Settings > Developer > API Access Tokens; the provider documents immediate revocation on deletion. For a HighLevel private integration the operator selects the exact integration and either deletes it or rotates with immediate expiry; deferred seven-day rotation does not qualify. OAuth installations use the exact selected sub-account uninstall procedure, never agency-wide uninstall. There is no invented revoke, introspection, cancel-all or arbitrary provider control endpoint. [Chit Chats API authentication](https://chitchats.com/docs/api/v1), [HighLevel private integration management](https://help.gohighlevel.com/support/solutions/articles/155000003054-private-integrations-everything-you-need-to-know), [HighLevel uninstall scope](https://marketplace.gohighlevel.com/docs/ghl/marketplace/uninstall-application/).

`verify_retirement` requires that original source/action-bound receipt, writes an exclusive verification intent and then requires a real old-credential `401` plus successful replacement reads on the selected scope. A `403`, wrong tenant, malformed response, redirect, missing receipt or still-usable credential refuses verification. An OAuth installation additionally makes exactly one supported refresh-grant probe using the privately supplied selected client ID, client secret and old refresh token. Only `invalid_grant` on HTTP `400`/`401` is accepted as that refresh credential's denial; `invalid_client`, an ordinary access-token expiry, a usable refresh or an unknown response is insufficient. A successful refresh can rotate a single-use token: the result is discarded, remains unresolved and is never replayed. Both the client and exclusive attempt receipt prevent automatic replay after loss. Recovery observation is read-only and must reuse the original receipt without probing refresh again. These checks establish the selected credential observations; they do not establish completeness of all historical credential chains or inbound webhook retirement. [Refresh-grant API](https://marketplace.gohighlevel.com/docs/2021-07-28/ghl/oauth/get-access-token/index.html).

The original receipt fixes credential provenance, tenant/client, reviewed provider IDs, source and action identity, and retains the safe actual fixed-query before-snapshot. The reviewed database digest identifies this PREstate. It does not require another reviewed artifact for a declared callback transition. A source-owned reducer permits only the exact OAuth `AppUninstall`/`UNINSTALL` persistence: the same connection becomes `revoked`, its stored credential is actually the revoked sentinel, its immutable expiry/location remain unchanged, and one matching webhook receipt is added at the exact transaction update timestamp. Every prior receipt and every contact, effect, outbox and marketing row must remain unchanged. Other new effects, principal drift, suppressed updates, missing receipts or unrelated business changes remain unresolved. Provider access and refresh denial are still required. The reducer publishes the separate current snapshot digest and transition observation while preserving the original artifact and receipts. `observe_retirement` replays only reads and this bounded reducer during recovery; it never repeats the refresh grant or rewrites either original receipt.

The source exports fixed `database_queries` for the coordinator's read-only, repeatable-read bridge. It must execute every query, bound to the selected private database, before and after provider observation. It must reject changes outside the declared reducer, changed lease/control/source bindings and incomplete results. SQL selects shipment and job identity/status/version/lease/unknown-outcome references, hashed idempotency keys, tenant-bound CRM contacts/effects, global unscoped CRM outbox/HighLevel delivery rows and selected connection/webhook receipt state. It excludes credentials, ciphertext, message bodies and plaintext emails; a fixed SQL equality expression exposes only whether stored credentials equal the revoked sentinel. Contact matching compares the database's normalized-email digest with a private provider read. Canonical snapshot SHA-256 uses recursive sorted keys, compact ASCII JSON and no nonfinite numbers; timestamps are explicit SQL text. An assertion such as `complete: true` cannot replace the actual fixed-query shape or reviewed digest.

For Chit Chats, unfiltered shipment counts bracket every complete paginated inventory. Duplicate IDs, truncated/inconsistent counts, limits, unexpected reviewed IDs and drift refuse. Every recorded provider shipment is retrieved and compared with the inventory, its database ID, public order reference, selected postage and authoritative `purchase_amount` in CAD. Only matching `delivered`/`voided` provider and stored outcomes are terminal. A job also needs an exact recorded identity/idempotency digest, supported type, payload hash, successful completion, cleared lease and no unknown outcome. Pending/refund-requested states, missing provider IDs, unmatched provider objects, retries, dead letters, legacy notification delegation and unknown results remain unresolved. Two stable full inventories plus exact stored receipts can produce numeric zero for this selected staging client and database snapshot, including a nonempty terminal fixture. This is not financial reconciliation, historical-writer fencing or proof that a retired producer had no unrecorded in-flight request. Those independent conditions remain the coordinator's responsibility. [Provider shipment count, pagination and object reads](https://github.com/chitchats/chitchats-api-doc/blob/master/sections/shipments.md).

For HighLevel, complete contact searches and current workflow search pages bind the selected tenant. Known contact/entity, note, completed-task and terminal-opportunity observations bind provider IDs and database/idempotency references; changed, missing and pending outcomes remain unresolved. Workflow definitions and accepted enrollment receipts do not prove execution completion. The current workflow logs API has limited account availability and retains only 60 days; an empty time window cannot prove that older executions or downstream messages have drained. The component therefore retains `activeExecutions: null`, `uncertainEffects: null`, `workflowExecutionInventoryComplete: false` and `inboundWebhooksQualified: false`, even when every known CRM effect reconciles. Unknown account permissions, webhook subscriptions, historical runs and accepted downstream delivery stay open. [Contact search](https://marketplace.gohighlevel.com/docs/ghl/contacts/search-contacts-advanced/), [workflow search](https://marketplace.gohighlevel.com/docs/ghl/workflows/search-workflows/), [workflow log retention and availability](https://marketplace.gohighlevel.com/docs/ghl/workflows/get-workflow-logs/).
