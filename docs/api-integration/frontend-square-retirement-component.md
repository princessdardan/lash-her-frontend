# Dedicated staging Square sandbox retirement readback

This component is source-only. It neither authorizes live staging nor establishes whole P2-00 fencing. Existing Dardan release review/start remains the operator boundary. Production R04, production Square, and shared credentials are excluded.

The exact reviewed provider bindings artifact selects `squareRetirement`: sandbox PAT, `LE2H76M5V90AM`, a reviewed merchant ID, `sandbox-sq0idb-*` application ID, API version `2026-05-20`, and only staging callback `wbhk_b8cf77ce0a5142b38b93715c05ede7d5`. Runtime suppliers privately resolve replacement/retired credential references; token values never enter arguments, environment, receipts, error bodies, or hashes. The fixed provider client accepts only the sandbox HTTPS origin, exact location/subscription, and exact payment/refund GETs. Its only mutation disables that selected callback. There is no charge, capture, refund, cancellation, enable, token creation, or production path.

Square documents [revoke-token](https://developer.squareup.com/reference/square/o-auth-api/revoke-token) for OAuth tokens. This package does not apply that operation to a PAT. [Token status](https://developer.squareup.com/reference/square/o-auth-api/retrieve-token-status) requires production authorization; this package does not use it to qualify sandbox credentials. No documented PAT retirement API was established. The existing operator must perform the supported sandbox credential retirement through the provider dashboard, then this code verifies actual denial. A checkbox or evidence hash cannot supply that result.

Reviewed sequence, under the existing environment and physical migration locks:

1. Deploy the admission-compatible source with all ten P2 flags false, `LASH_P2_CERTIFICATION_SCHEDULES=off`, and replacement sandbox runtime configuration. Protected `square-binding` mode uses the deployed `SQUARE_ACCESS_TOKEN` for [RetrieveLocation](https://developer.squareup.com/reference/square/locations-api/retrieve-location). It returns only fixed location/merchant/currency/country/status and the deployed application ID. Location access proves merchant access, not independent token-to-application introspection.
2. `suspendFrontendSquareCallback` verifies that protected runtime, verifies that the old credential can access the same sandbox location, writes durable pre-retirement evidence, and disables/readbacks only the selected staging subscription using [UpdateWebhookSubscription](https://developer.squareup.com/reference/square/webhook-subscriptions-api/update-webhook-subscription). Existing subscription details and signed callback URLs remain private. Lost acknowledgement or an existing intent refuses replay.
3. Dardan retires the exact old sandbox PAT using the existing provider dashboard controls in the reviewed action. No production/shared token is selected.
4. `verifyFrontendSquareCredentialRetirement` requires original pre-retirement evidence and a fresh deployed runtime probe. The replacement credential must retain exact location access. The old credential must return HTTP401 with Square `AUTHENTICATION_ERROR`/`UNAUTHORIZED`;403, timeout, bad response, or continued access cannot qualify. Both protected runtime and subscription disabled state are checked again.

`frontend-square-effects.mjs` reads only reviewed booking-payment-attempt/product-refund IDs in a read-only repeatable-read transaction on the parent's physically verified DB client. It never selects buyer/contact/card/credential fields. It hashes the real immutable idempotency key, amount, provider IDs, references, and stored status; these rows must match reviewed artifact hashes. The worker then retrieves those exact provider IDs and compares CAD amount, sandbox location, payment application/reference/order, or refund original payment. Provider and stored terminal statuses must agree before `storedOutcomeConsistent=true`.

Missing provider IDs remain unresolved; there is no safe idempotency-key lookup here and no replay to discover an outcome. Pending/approved outcomes and differing immutable values remain unresolved. This comparison performs no domain finalization or ledger completion. Additional financial producers, historical preview/local subscriptions, database/provider bindings, running invocations, and unrecorded effects still require exhaustive inventory/reconciliation. Consequently overall active/uncertain counts remain null even when every selected stored effect agrees. Credential denial and callback disablement alone never authorize SQL or restoration.

Isolated verification: `python3 -B -m unittest frontend_square_retirement_test` from `ops/platform/host`; protected TS tests cover fixed sandbox TLS, rejected redirects/401/oversized responses, source/environment isolation, and missing dependencies. These use owned loopback servers only. Real staging dashboard/runtime/effect qualification remains open.
