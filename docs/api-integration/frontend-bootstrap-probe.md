# Protected frontend admission bootstrap probe

`GET /api/internal/release-probe` retains its existing expiring private credential, workload SDK and challenge binding. The explicit `x-lash-release-mode: admission-bootstrap` mode is staging-only and additionally verifies the deployed frontend's actual database admission configuration. Unknown modes refuse before outbound work. `HEAD` remains nonexecuting.

The runtime opens a short repeatable-read, read-only PostgreSQL transaction with verified TLS and the exact configured database, runtime user and server major. It calls the scoped `frontend_admission.current_policy` function with the actual source/producer and requires both controls closed. It hashes public schema catalog metadata using the same structural queries as the locked operator. Runtime journal access must remain denied: the private applied-lineage hash stays in the operator receipt and is independently rechecked on the original physical-lock backend.

The response contains the existing challenge/project/source/gateway identity, `checks: ["gateway-course-catalog", "frontend-admission-bootstrap"]`, an `admission` object, top-level `schemaCatalogSha256` and `featureControls`. It includes no credentials, database usernames, schema definitions, row data or migration journal. All ten later feature controls must be literal `false`, including the independent lifecycle recovery and learning-route controls. This probe performs no admission begin/settlement or application writes; its direct PostgreSQL constructor is a reviewed read-only inventory surface.

The ordinary workload check uses the explicit Course gateway alias `/course/v1/courses`. The preapplication release must verify the existing gateway supports that alias or prepare the compatible gateway artifact before bootstrap. An incompatible gateway fails the actual probe and prevents promotion, fencing and application SQL. There is no route fallback or inferred compatibility.

Six focused handler cases and four grouped actual-route PostgreSQL 16 checks pass. The owned HTTP bridge executes the real route, current SDK transport, TLS runtime connection and catalog queries. It verifies the runtime hash against an independent operator hash, unchanged schema/operation count, denial for every enabled feature, open admission/recovery and an unregistered source. Gateway data and workload identity are synthetic; no live provider or database is used. The same parent run passes all 83 migrations, seven identity tests, six lifecycle cases and existing admission fixtures. The first owned probe attempt retained a failure caused by a fixture expecting the pre-P2 gateway path; the corrected fixture tests the explicit service alias without changing application behavior.

This is a bootstrap qualification component. It does not establish historical/provider fencing, zero uncertain external effects, SQL authorization, staging acceptance or G2.
