## Approved agreement

The [normative bundle README](../../../contracts/api-integration/v1/README.md)
and hashed schemas specify the wire contracts. The owner decision covers:

- Immutable customer UUID subjects for learners/members and separate admin UUID
  subjects; four distinct audiences and independent signing keys. Closed v1
  claims, HS256, integer timestamps, maximum 300-second user-token lifetime,
  maximum 30-second skew, and verifier-first overlapping key rotation.
- Explicit capabilities: course-editor for catalog/curriculum/video authoring,
  course-support for administrator entitlement operations, and
  community-moderator for moderation. None implies another capability or grants
  access to service-only or account-lifecycle routes.
- Separate credentials for frontend entitlement commands, Course event
  publication, Community authority reads, and each API's lifecycle commands.
  Preserve the existing exact 300-second event/read JWT contract; use bounded
  300-second entitlement/lifecycle tokens. Deployment bindings stay downstream.
- Existing Course and Community error envelopes, operation-specific response
  schemas/statuses, noncoercing parsing, and safe request correlation.
- Header/body idempotency equality and the shared immutable entitlement namespace;
  identical replays retain the stored result and semantic reuse returns 409.
  Frontend retains financial/provider/outbox ownership.
- Community-owned strict enrollment events, UUID/state/version/UTC invariants,
  canonical digests, replay/conflict handling, and online Course authority.
- A target lifecycle command stream starting at 1 with consecutive versions, all
  actions delivered to both APIs, transactional receipt/effects, HTTP 200
  accepted/duplicate receipts, and exact replay checked before stale/deleted
  rejection. Conflicting IDs, gaps/stale versions and new post-delete commands
  return 409 with receiver-specific codes. Delete is terminal; delayed events
  cannot recreate identity. New exports after delete are rejected; any retained
  record request uses a separate authorized frontend process. Financial/audit
  retention and private export retrieval remain required.

The capability route assignment and explicit lifecycle response/retry/post-delete
rules clarify the October 4 draft. Dardan explicitly accepted them before release.
No new lifecycle endpoint has been added to either implementation's OpenAPI.

## Release procedure and evidence

Prepare a contract-only frontend commit, retaining unrelated working-tree changes
in their original checkouts. Include bundle bytes, generated declarations,
validators/tests, locked dependencies, contract CI drift check, and this decision.
Hash normative prose as well as schemas. Use an immutable full frontend commit
SHA and annotated tag `api-integration-v1.0.0`; do not move or overwrite the tag.
Publish the release branch `codex/p1-01-contract-v1` and tag without changing
main/staging or activating application deployment. Record a separate evidence
commit that binds the frontend bundle SHA and both API SHAs, exact commands,
results, baseline SHA, and publication readbacks in the canonical tracker.

For this first release the approved bundle is its own initial baseline.
Self-comparison establishes exact-byte reproducibility only. Compatibility with
an earlier integration release is **not applicable**; no earlier bundle exists.
Future candidates must compare against this immutable v1 commit's archived bytes.

The release check must verify both bundle directories against full Git SHAs,
verify upstream source bytes, and reject missing/mutable revisions, modified
normative prose, candidate baselines and incompatible wire changes. Run generation
and contract tests from the exact release checkout and attach their outputs.
