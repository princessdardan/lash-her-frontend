# CRM and marketing sync recovery admission

This source component covers `runHighLevelWorker` and the marketing contact-sync worker. Both acquire independent recovery admission before pause-cancellation queries, job claims, provider calls, compensation, or receipts. Their authenticated cron handlers invoke these boundaries after authentication; direct exported worker calls use the same boundary. Admission remains disabled by default.

CRM retries/reviews and marketing claim/provider failures retain uncertainty even when the domain catches the error and persists a retry. A missing lock-qualified CRM completion, effect/contact/offer projection, marketing completion, or Resend contact/segment/topic acknowledgement also retains uncertainty. Best-effort Resend event failures retain uncertainty without changing off-mode behavior. Worker loops and unsubscribe compensation finish before settlement; worker-path consent queries run sequentially so a rejected sibling cannot outlive the operation.

The focused `remaining-workers.test.ts` uses the real admission runner with an intercepted ledger transport and injected worker repositories/providers. It covers closed recovery, independent new-work closure, caught errors, absent receipts, unsubscribe compensation in flight, connection/settlement loss, authentication, and off-mode summaries. These are source-level tests, not owned PostgreSQL or deployed worker qualification. Existing HighLevel and marketing worker regression tests also run.

Still required: actual business/ledger database receipts and race qualification, provider acknowledgement contracts for existing opaque HighLevel projection writes, immutable deployment execution, complete producer/provider inventory, historical fencing/bootstrap, and parent release coordination. This component neither enables admission nor authorizes pending SQL or staging release. P2-00 remains incomplete.

## Remaining maintenance and inventory source boundaries

Retention cleanup and rate-cache refresh are **new-work**: they perform proactive maintenance, including creating new representative provider drafts. They do not receive recovery permission merely because a cron schedules them. Sanity product-event inventory reconciliation is **recovery**, while direct stock set-point/untrack helpers and the stock backfill are **new-work**. A per-stock-batch context owns nested helpers so a newly closed fence cannot split an already admitted batch between callbacks and writes.

The rate refresh retains uncertainty for each caught create/write failure and failed ephemeral-draft cleanup, continues/awaits the remaining cells, and verifies the cache upsert receipt. Existing off-mode partial summaries and best-effort cleanup behavior remain. Retention runs sequentially through its existing steps and its HighLevel/shipping cleanup; a failed step leaves the operation uncertain. This does not alter approved retention windows or change shipping-retention implementation owned by the shipping workstream.

Stock sync checks selected-row update/delete receipts and confirms an exact target after a concurrent insertion conflict. Both Sanity entry points retain HMAC validation. The dedicated callback returns private retryable 503 for admission refusal. The product revalidation fold-in uses the existing admission configuration resolver: enforced or malformed enforcement awaits/refuses before acknowledging the stock work, returning 503/no-store/retry-after rather than losing the provider retry. Off mode retains the existing `after` path and that legacy deferred path remains unqualified. Cache tag invalidation remains independent of stock writes.

Seven added source cases cover maintenance classification/refusal, all-cell rate cleanup, provider/write/cleanup uncertainty, off-mode summaries, every direct stock export's malformed-enforcement refusal, awaited product responses, and retryable Sanity refusal. These tests still use injected repositories/providers and ledger transport; no real carrier, live database, deployment, admission setting, or schema was changed. Owned database tests must qualify actual stock/cache/retention receipts, locks, transactions, and fault behavior before claiming whole-operation qualification.
