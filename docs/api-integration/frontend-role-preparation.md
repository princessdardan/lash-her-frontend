# P2 staging frontend role preparation

This source-owned component supplies the role prerequisite that admission bootstrap intentionally does not create. It prepares only the fixed new roles `lash_her_frontend_staging_admission_owner_p2` and `lash_her_frontend_staging_runtime_p2`. It does not change historical P1 roles, apply application migrations, create the admission ledger, enable features, deploy code, or touch providers. Its receipts do not authorize application SQL.

`prepareFrontendRolesPlan(candidate, job, specification)` validates a qualified staging P2 candidate and its exact frontend source/contract/image/SQL job bindings, direct target and recovery reference. The specification is `{version:1, producerSha256:[...]}`. The public frozen plan contains the candidate/job/target hashes, fixed role attributes and grant scope. It contains no invented OIDs or credentials. PostgreSQL assigns OIDs during apply.

`applyPreparedFrontendRoles(plan, client, dependencies)` runs in-process on the parent's already connected physical TLS client. Dependencies are `confirmation: staging/<actionId>`, `verifyEnvironment`, `verifySession`, `directory`, and `privateDirectory`. The two directories must already be private mode-0700, owned by the operator, outside a Git checkout, and canonical paths. Use a dedicated preparation receipt subdirectory: the existing coordinator requires its own main receipt directory to start empty. The preparation API acquires neither flock nor a second PostgreSQL lock. It independently verifies the actual held frontend migration advisory lock, unchanged physical PID, authorized TLS, explicit connection host/port, actual current/session user, database, major version and writable transaction at each stage. Parent callbacks must verify their actual environment flock/session rather than return caller booleans.

Preparation generates a 384-bit random runtime password, atomically and exclusively retains the private password/URL file mode-0600 with file/directory fsync **before** role SQL, then retains a public durable intent. It re-reads the private file before beginning and before committing. Role SQL transmits a locally generated SCRAM verifier rather than the plaintext password. SQL text, credentials, verifiers and raw errors are never copied to public receipts or console output. The selected client's query tracing and database statement/audit logging must preserve that private credential boundary; the owned fixture verifies that its server logs contain neither passwords nor SCRAM verifiers.

One transaction creates the NOLOGIN/NOINHERIT admission owner and the distinct LOGIN/NOINHERIT runtime. Both are explicitly NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOREPLICATION and NOBYPASSRLS. The owner receives database CREATE, which PostgreSQL requires to create the independent admission schema through the operator's explicit SET ROLE. PostgreSQL does not offer a grant limited to creating one named schema. The owner receives no persistent object ownership before bootstrap and no public table/sequence/default grants. Its role cannot log in.

The runtime receives CONNECT, public USAGE, table SELECT/INSERT/UPDATE/DELETE, sequence USAGE/SELECT, and the corresponding public default grants for objects subsequently created by the migration operator. It has no outbound role membership, ownership, persistent database/schema DDL, journal schema/object access, grant options, extra table privileges, or unrelated direct grants. Actual effective privileges and direct/default ACLs are read back and retained with actual role OIDs before commit and again after commit. Inherited PUBLIC TEMP is recorded and preserved under the existing approved runtime policy; PUBLIC and old-role ACLs are not changed. Direct privileges, ownership and memberships outside the fixed policy refuse rather than being silently repaired.

PostgreSQL 16+ automatically grants a role created by a non-superuser CREATEROLE operator back to that operator with ADMIN TRUE, SET FALSE, INHERIT FALSE, as the bootstrap superuser. The creating operator cannot revoke that automatic grant. The component verifies and records only these exact inbound creator grants plus an owner-only, non-inheriting operator SET grant. The runtime itself gains no membership in the owner, operator or another role. This behavior was reproduced using an actual non-superuser CREATEROLE operator, rather than qualifying only a superuser fixture. See [role attributes](https://www.postgresql.org/docs/16/role-attributes.html), [CREATE ROLE](https://www.postgresql.org/docs/16/sql-createrole.html), [GRANT](https://www.postgresql.org/docs/16/sql-grant.html), and [ALTER DEFAULT PRIVILEGES](https://www.postgresql.org/docs/16/sql-alterdefaultprivileges.html).

An existing name is refused by default. Explicit reuse requires `specification.reuse: {ownerOid,runtimeOid,proofSha256}` and dependencies `reuseDirectory`/`reusePrivateDirectory` pointing to a previously successful, retained source-owned preparation outcome and its private credential file. The prior public proof hash and actual current names, OIDs, flags, ownership, memberships and exact allowed grants are rechecked. The retained password must authenticate as the actual selected runtime over verified TLS. Both roles are reused together; partial/unrelated roles are never coerced. Already bootstrapped admission ownership is outside this preparation policy and must use the existing reviewed lifecycle instead.

On success, public output contains `owner`, `runtime`, `producers`, `observed` privileges and `proofSha256`. The explicit, **nonenumerable** in-process `result.private` contains `runtimeDatabaseUrl` and `credentialReceiptRef`. Ordinary JSON serialization therefore excludes both. These observed OIDs can materialize inventory owner/producers, and the private URL can feed the driver/broker without another approval or lock acquisition. The driver retains the same environment flock and physical migration session while composing later independently authorized stages.

Every action directory is exclusive. An existing intent, outcome or private credential file blocks another invocation. Failure retains the original intent, credential material and any completed observation. A known rollback is recorded as `rolled-back`; a missing credential before role SQL is `not-started`; an actually committed transaction whose response was lost is `commit-acknowledgment-unknown`. No unknown commit is rolled back or replayed automatically. A committed role transaction followed by failed verification remains committed and requires review. A new deliberate recovery decision must inspect actual state and preserve these records.

## Standalone entrypoint

`node ops/platform/prepare-frontend-roles.mjs candidate.json job.json roles.json` defaults to offline plan mode. Explicit `--plan` is also supported. It reads no migration credential and opens no connection. Apply requires:

```sh
node ops/platform/prepare-frontend-roles.mjs --apply candidate.json job.json roles.json \
  --confirm staging/<actionId> --receipts /private/operator/roles-receipts \
  --private /private/operator/role-credentials
```

`FRONTEND_ROLES_MIGRATION_PRIVATE_DIRECTORY` names a private directory containing mode-0600 `migration-connection.json` with the runtime-private `databaseUrl`. Credential values never appear in arguments. This file must contain the selected direct migration URL with only `sslmode=verify-full`. Apply verifies the clean exact candidate checkout, takes the existing native environment flock, acquires the frontend physical advisory lock once, calls the same in-process API, and releases its owned resources. Optional reuse directory paths are `FRONTEND_ROLES_REUSE_RECEIPTS_DIRECTORY` and `FRONTEND_ROLES_REUSE_PRIVATE_DIRECTORY`. The standalone command never invokes admission bootstrap, migration apply or the coordinator.

The actual TLS/SCRAM fixture covers native flock and physical advisory contention, target/user/OID/grant refusals, unrelated name preservation, private-file loss, transactional rollback, actual runtime authentication/CRUD, persistent DDL/journal/membership denial, owner SET ROLE schema ability, future-object default grants, exact approved reuse, old role/data/journal preservation, lost COMMIT acknowledgment with no replay, and absence of credentials from public receipts/server logs.
