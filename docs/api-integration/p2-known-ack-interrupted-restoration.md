# Interrupted known-ACK restoration C

C is an explicit new operator action for an interrupted, same-candidate known-ACK replacement. It restores the fixed ten-service runtime while admissions and native scheduling remain closed. It preserves the original gateway's recovery uncertainty of one; it never reclassifies that process as zero or recreates the original B success terminal.

## Eligible retained state

The original six causal files, ordered replacement intent/stage prefix, source-issued old-gateway stop and latest lineage, original fault lease/readback, original current-ready inventory, exact operator closure, and all 19 configuration input files must remain available and mutually bound. C consumes the original B formatters and serialization rules. A fresh configuration map cannot replace the reviewed original map. Root-owned input files and mounted runtime snapshots are separate objects.

C requires the original drop-after-ACK plan, one suspension witness, exact native-plan hash, original command/receiver/process binding, both durable canonical API ACKs, and the exact completed frontend operation with its original settlement hash. All unrelated frontend and API effects remain unchanged. Each new action rereads all three databases with a new physical FE lease, host flock, fresh eligibility deadline, current API schema/journal/role observations and a new process-local, single-use capability. Serialized receipts cannot reconstruct the old or new capability.

Earlier API-stage interruptions can qualify. An original gateway intent without readback qualifies only when the original installed B helper is exactly the reviewed frontier implementation, its replacement marker was never retained and is actually absent, and actual latest lineage remains the exact source-stopped old process with no newer or unmapped process. A pending/newer/contradictory lineage, present marker, changed helper, missing bytes or ambiguous older helper refuses. A proved running new-zero gateway uses ordinary recovery instead.

## Explicit command

Use Node 24 with reviewed private settings and a distinct restoration action ID. Planning does not perform provider or runtime actions. Applying requires the exact staging confirmation accepted by the fixed source entry. The private settings retain original candidate and receipt hashes; they cannot supply authority, counter exceptions, arbitrary containers or callbacks.

```sh
node ops/platform/p2-known-ack-interrupted-restoration.mjs plan /absolute/private/settings.json
node ops/platform/p2-known-ack-interrupted-restoration.mjs apply /absolute/private/settings.json --confirm staging/NEW_RESTORATION_ACTION_ID
```

The source entry verifies committed operator source/CI and uses the existing reviewed SSH installation and physical FE session. It does not apply SQL, prepare roles, change LOGIN, build/promote a frontend or open admission. Those actions cannot be requested through C.

## Replacement frontend database

Use `plan-profiled-current` and `host-plan-profiled-current` with version 2 settings and the exact `staging-current` qualification profile. Supply the original replacement release settings and the same `replacementRelease` selection used for the original bounded certification. The selection binds the absolute original guardian terminal path and raw SHA-256. The interrupted planner also requires the original certification plan, the exact retained causal receipts, and a distinct restoration action ID. Dardan starts the reviewed `apply-profiled-current` action with `--confirm staging/RESTORATION_ACTION_ID` after its preflight.

The interrupted observer verifies the full original apply-forward job and fresh read-only database state. It binds the named settled frontend operation and its original reconciliation digest, the exact login OIDs, both advisory locks and independent session closure. The guard preserves unresolved ledger rows if it has to close the ordinary recovery window.

Before later certification stages can run after either recovery outcome, the current runtime needs a separate lineage check. The original release receipt continues to refer to its immutable configuration. The successor proof must derive the active configuration path from the fixed prior action ID and join the raw host terminal, closure, gateway lineage and live ten-service runtime to the same original candidate and configuration hashes. This handoff remains open.

## Outcome and containment

Only a distinct new gateway with both admissions closed, active/uncertain zero, all ten current services and fresh three-database proofs can produce `P2_KNOWN_ACK_INTERRUPTED_RUNTIME_RESTORED_FENCED`. Frontend readiness and workload-probe freshness remain explicitly unverified, and traffic remains unauthorized. Existing deliberate forward recovery can qualify a later frontend after a proved new-zero runtime.

Loss or drift revokes authority, reaps registered children, stops the runtime, attempts metadata-only native disabling, and cleans both fixed readonly observer namespaces. A surviving broker contains a dead independent guard even before a worker exists. Concurrent abort/close paths serialize cleanup; uncertain child reaping retains the host FD and cannot produce a terminal. Failed readbacks remain unknown.

## Qualification boundary

The reproducible owned fixture executes actual isolated TLS/SCRAM PostgreSQL databases, all 83/22/11 migrations, actual application cron/dispatcher/canonical API receiver calls, a TLS gateway ACK-loss/replay, specific FE settlement, old-process/backend exit, a new process/FE backend/flock, fresh current probes, the fixed C five-stage sequence and journal comparisons. Docker/container transports, native provider metadata, Linux root installation, CI/SSH installation and the Node committed-source callback are projected or unexecuted in this fixture. It does not establish staging readiness or authorize a live action.

`validation.json` identifies exact frozen sources, commands, outputs, limitations and historical failures. The independent six-file prefix is captured from original B before C, checked unchanged afterward, and joined exactly to C's terminal. Outer B `domainProofSha256` retains its canonical-domain semantics; it is not a settlement-file hash.
