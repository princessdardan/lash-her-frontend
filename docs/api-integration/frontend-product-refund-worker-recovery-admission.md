# Queued product-refund recovery admission

Status: disabled-by-default P2-00 source component. Live admission, pending frontend SQL and all six rollout capabilities remain disabled. P2-00 remains incomplete.

The authenticated GET export at `/api/cron/chitchats-shipping` acquires an independent recovery entry for its queued Square product-refund batch. Admission precedes the Square-enabled check, candidate selection, expired-lease recovery and atomic claims, and remains active through each provider refund, refund/adjustment/obligation/order transaction and awaited policy-alert enqueue. Closing new work leaves this recovery class independent. Closing recovery refuses new batches before configuration or business access. Expired business leases do not drain an admitted operation.

Caught processing failures, nonsettled returned rows, pending/unknown provider outcomes, missing provider payment identity, rejected alerts and missing expected financial receipts retain uncertainty. A lost claim race remains a benign skip before provider mutation. Existing deterministic refund identities and no-auto-retry behavior remain intact. Enforced refusal or uncertainty returns sanitized `503`, `Cache-Control: no-store` and `Retry-After: 30`, before subsequent shipping operations run. With admission off, existing status codes, result counters, provider-identity fallback and incident-shaped exception responses are preserved; the shared uncertainty markers are no-ops outside admitted work.

The entry ends after the refund batch. Quote abandonment, tracking enqueueing, shipping operations and shipment PII redaction still execute separately and remain unqualified. This component does not qualify the entire shipping route or direct drain/process/admin callers. A successful refund batch cannot establish drain for those other executions.

The [validation record](baselines/2026-11-05-p2-00-product-refund-worker/validation.json), source inventories, classification and effect audit bind the component to its implementation. Controlled tests cover authentication, closed and independent admission, disabled/empty/off behavior, query/processing/alert failures, later-row processing, held stages, acknowledgement loss and the explicit downstream boundary. The actual-route loopback/TLS-ledger/migrated-database fixture covers settled/pending/rejected/failed/mismatched/missing-identity provider responses, expired leases, missing refund/adjustment/obligation/order receipts, closure during provider work, closure during a blocked settlement transaction and actual ledger-backend death. Provider requests are intercepted and checked against the stored idempotency key and immutable payment/amount/currency; unexpected requests refuse. Unresolved entries prevent drain/restoration until all work finishes and the fixture owner deliberately reconciles hashed outcomes.

These checks use synthetic provider responses, rows and producer identities through a test HTTP bridge. They do not qualify deployed Next.js/native execution, real provider drain, historical producers or the parent release/restoration coordinator. Exact-head CI remains required. No live database/provider/credential/scheduler change or admission/pending-SQL enablement is included.
