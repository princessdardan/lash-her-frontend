# Deliberate frontend admission restoration

This is an optional final stage of the reviewed staging coordinator. It is not reachable through the legacy pending-SQL CLI. It opens only current source-registered frontend admission; historical logins, retired provider ingress, and native schedules remain closed. It does not claim P2-00 or staging acceptance.

The reviewed inventory selects `restoration`: version1, boolean `recovery` and `newWork` (new work requires recovery), `nativeSchedulesEnabled:false`, `providerIngress:"keep-retired"`, and the hash of the exact normalized `gatewayObservation` provider binding. The latter records the existing host machine/release/candidate, public runtime/gateway configuration hashes, and pinned gateway image. Runtime context privately selects its existing protected configuration directory; no credential values are fetched or returned. Existing Dardan release review/start supplies authorization. There is no new signer, separate executor, or per-step approval.

The physical migration client and environment flock remain held throughout:

1. Apply reviewed SQL and verify it. Deploy/promote the compatible frontend and independently verify it and every external fence.
2. Complete the migration core's post-continuation journal/schema/runtime checks and durable continuation receipt. Its new in-process `afterContinuationVerified({database,verifySession})` hook follows those checks and precedes advisory unlock/client end. A failed check, missing receipt, lost session, serialized callback or absent compatible continuation cannot enter finalization.
3. Recheck actual public catalog and applied journal against that exact database receipt, current deployment/source/workload receipt/native schedule state, every external provider fence, current producer source/OIDs/runtime privilege profile, historical NOLOGIN identities, and zero historical sessions. Unknown effects refuse.
4. Observe the actual host gateway without changing it: exact Linux machine; reviewed existing configuration bytes; one healthy running gateway container with exact image and Compose labels; read-only mounts of the selected configuration/admission directory; actual internal `/admission` response matching the durable state file hash/source/candidate, with numeric active/uncertain counts. It must already have the exact reviewed desired admission flags and zero uncertain operations. The observer does not change host admission or start/restart any process.
5. Record a durable recovery intent. Open selected frontend recovery, verify actual current epoch/controls and boundaries, then record its success. Only then record/open selected new work and repeat the checks. Recovery-only is a complete supported profile. A selected no-op is independently checked and avoids an unnecessary epoch mutation.

Every opening is a distinct durable intent followed by a real transaction and independent readback. Existing operation rows prevent an opening while unresolved frontend work exists. Both physical locks remain held until all source checks/receipts complete.

A failure never opens another stage, reissues an uncertain opening, restores LOGIN, replays SQL, enables native scheduling, or overwrites original receipts. If a process dies after recovery opens, that explicitly selected recovery stage may remain open while new work stays closed. A lost COMMIT acknowledgement reports flags as unknown. The existing read-only recovery action observes actual epoch/control/provider state; it cannot perform restoration. Any deliberate subsequent change requires a new reviewed action based on those actual observations. Opening a frontend flag alone does not replace host/provider qualification.

`ops/platform/test-frontend-restoration-local.mjs` owns a fresh PostgreSQL16/18 TLS cluster and loopback provider model. It tests actual process death, backend termination, lost COMMIT acknowledgement, interrupted durable receipt, unknown effects, historical LOGIN drift, lock contention, recovery-before-new-work, and real read-only Square financial queries. Run with `FRONTEND_RESTORATION_LOCAL_TEST=true PG_BIN=/absolute/postgresql/bin node ops/platform/test-frontend-restoration-local.mjs`. It accepts no configured/live database. The shared parent release harness is unchanged.

Remaining release integration: the integration owner must normalize this optional restoration field in `frontend-release-inventory.mjs`; all whole-source/provider inventories and live staging checks still have to pass. The concrete whole-fence adapter continues to refuse unresolved vendor/effect coverage. Native schedule/provider ingress restoration and any gateway mutation require their own exact qualified profile and are intentionally not inferred from this frontend stage.
