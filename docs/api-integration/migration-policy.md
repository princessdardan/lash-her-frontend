# Cross-repository migration policy

Effective 2026-10-01; resolved by [P0-02 / D-02](decisions/2026-10-01-p0-02.md). Applies to frontend, Course, and Community integration releases. Each repository owns its own schema, migration files, credentials, and database.

## Policy and implementation status

Production **forward migrations are permitted only through an approved, protected release job**, after the same migration artifact passes staging. Routine local/operator shells, application startup, tests, seed scripts, round-trip tooling, schema push, and ad hoc SQL are not production migration paths. Production test/seed restrictions remain absolute. A target label or confirmation variable is not release approval.

This is the required procedure, not evidence of a working release system. P0-01 found no coordinated protected release workflow or complete migration images. P1-04 owns migration artifacts/locking, P1-05 owns required CI, P1-07 proves staging execution, and P6-01 establishes protected production promotion. Until those controls exist and are verified, integration production migrations are blocked. P0-02 does not authorize running any migration.

## Existing command semantics

Commands run from the owning repository root with Node.js 24. Credentials must be injected by the job, never included in command arguments, logs, or documentation.

It does not enforce protected-job approval, an environment lock, or a complete applied-lineage comparison.                                  |
| Community  | `DATABASE_TARGET=staging`, `STAGING_DATABASE_URL`                                        | `DATABASE_TARGET=production`, `PROD_DATABASE_URL`                                                                                      | Same Drizzle limitations as Course. Use an explicitly exported job environment; `drizzle.config.ts` does not load `.env` itself.                                                                                 |

Both APIs accept `dev`/`development` and `prod`/`production` aliases. Explicit named targets take precedence over legacy `DATABASE_URL`; a missing named URL must not be replaced with another environment's URL. Do not use the legacy fallback for release jobs. Course loads `dotenv/config`; frontend also loads `.env` by default, not Next.js `.env.local`. Release artifacts must contain no `.env` files and must receive only the intended database credential. Use direct, non-pooled API migration connections. Frontend connection handling remains as documented in its [private database runbook](../private-database-migration-runbook.md).

## Protected release procedure

1. **Pin and review.** Record the three repository commits, runtime image digests, migration artifact digests, contract hashes, ordered journal entries, and SQL SHA-256 hashes in the release manifest. Build separate migration artifacts from the owning revisions with the SQL, journal, configuration, Node 24, and migration tooling. Current API runtime images are insufficient. No uncommitted migration is a release artifact.
2. **Prove compatibility.** Require green checks on those exact revisions, isolated PostgreSQL 16 clean-install and data-bearing upgrades, schema drift checks, and guarded rollback/refusal coverage. Validate compatibility with each deployed database major version, including the frontend PostgreSQL 17 target observed in P0-01. Rehearse locking/backfill time and compatible application rollback. CI test credentials must never provide access to staging or production.
3. **Approve the target.** Resolve provider/project/branch/database/host identity from the release environment and compare it to an independently maintained approved target. A variable called `PROD_DATABASE_URL` is insufficient proof. Confirm backup/PITR and an isolated restore rehearsal. Record operator, verifier, approver, exact artifact, maintenance window, and smoke plan. Production credentials become available only after the protected environment's approval gate.
4. **Serialize and preflight.** Acquire a release lock keyed by service and actual database/environment. Hold it across preflight, migration, and verification; prevent concurrent manual and automated runners. Inventory the entire applied journal and compare timestamps and SQL hashes against the pinned artifact. Reject unknown entries, changed hashes, gaps, duplicate timestamps, and unexpected pending migrations. Frontend uses `npm run db:check` with its audited lineage policy; API jobs must provide equivalent read-only comparison before invoking Drizzle. `drizzle-kit check`, schema drift, or the latest migration number alone does not verify a deployed database. Do not create journal rows to make this check pass.
5. **Apply staging once.** Run `npm run db:migrate` with the staging selection above. Apply only the reviewed pending forward chain, before dependent code starts. Keep required write freezes and disabled publishers in place for the entire backfill. For Course 0014, rehearse the exclusive locks and UUID/case-collision checks documented in the API cutover runbooks. A failed run blocks dependent rollout; inspect the resulting state before considering a separately approved retry.
6. **Verify staging.** Re-read the complete journal, confirm intended constraints/indexes, execute staging application/worker smoke checks, and record sanitized evidence. Deploy compatible receiver/read APIs before dependent writers/publishers and frontend features. Tests that create/drop schemas or run down migrations stay on disposable loopback databases.
7. **Promote production.** Reuse the exact verified migration artifact and API digests. Obtain production-specific approval, target/backup checks, lock, and fresh lineage preflight; then invoke `npm run db:migrate` with the production selection above inside the protected job. Do not substitute a staging-configured frontend build for the production-configured deployment.
8. **Record and unlock.** Verify the complete post-migration lineage, schema, readiness, and approved production-safe smoke checks before admitting dependent traffic. Store job URL, approver, timestamps, target identity without credentials, pre/post journals and hashes, applied files, backup reference, smoke results, and rollback/forward-fix decision. Release the lock only after the outcome is recorded.

## History and failure rules

Never rewrite applied SQL, snapshots, or migration journal rows, discard audit/business data, or use a schema push to repair drift. Use a reviewed forward migration. Down scripts are for guarded disposable tests; they are not a routine production rollback mechanism. Stop affected writes/sales on failure while preserving safe financial reconciliation and recovery. Restore compatible application artifacts or roll forward. A database restore is a separately approved incident recovery operation with reconciliation of subsequent financial/events history, not a normal deployment rollback.

The P0-01 read-only inventory found Course dev/staging/prod through 0013 with 0014–0016 pending; this does not prove that 0014 has never been applied elsewhere. P0-04 must compare committed and working 0014 SQL/snapshot/journal bytes, identify every deployment target, and record applied hashes and provenance. If an earlier 0014 exists anywhere, preserve that applied version and carry the changes in a new forward migration. If it is demonstrably unapplied everywhere, record the reviewed candidate bytes and commit them before release. Unknown provenance blocks release. Community 0008 also needs provenance review and target lineage evidence; its database was not inspected in P0-01.

Never weaken or bypass `assert-test-database.mjs`, Course `assert-seedable-database.mjs`, target validation, or round-trip refusal guards. Test and round-trip databases remain isolated and disposable on loopback PostgreSQL. Course seed is forbidden in staging and production. Community has no seed command; that does not permit ad hoc production seed SQL.
