Operational flowcharts

Lash Her checkout and booking flows

Three code-aware diagrams for training program checkout, service booking, and product checkout. Each step names the UI surface, server route, storage boundary, data source, and provider involved.

Training checkout Service booking Product checkout Shared boundaries
CMSSanity stores public/editorial content, product records, and training-program content. Service detail-page imagery and SEO may link to operational offerings, but booking settings and offering configuration do not live in Sanity.

Flow 01

Training program checkout

A student buys a training program through Square (Web Payments SDK), the app stores the paid enrollment in private Postgres, then issues a tokenized scheduling link for the intro call.

Square + private Postgres + Google Appointment Schedule

User inputNo index

3

The checkout button fetches the public Square config, renders Square's hosted card fields, and tokenizes the entered card into a single-use payment token. The card PAN stays inside Square's iframe and never reaches the server.

Client SDKPII boundary
Code and data

4

Server validates and reserves the private order and enrollment

The training checkout API reloads the Sanity program, rejects stale or unsupported cart-like input, and reserves a pending Square training order plus a training enrollment snapshot in private Postgres before charging. Secrets are hashed/encrypted before persistence.

API routePrivate DB
Code and data

/api/training-checkout uses validateTrainingCheckoutRequest and reserves the order via createPendingSquareTrainingCardOrder. checkout_orders stores the pending Square order with purpose training; training_enrollments stores native program checkout snapshots, checkout email, scheduling status, and later token hashes.

5

Server authorizes and captures the Square payment

Using the tokenized card, the server charges the reserved amount through Square with an authorize-then-capture sequence, a deterministic idempotency key, and void-on-failure compensation, recomputing the amount and currency from trusted order state.

Provider callIdempotent
Code and data

The Square training checkout orchestrator (key namespace square-training/<orderId>) runs the shared authorize→capture→void core and hands off to the Square training card finalizer once the capture is approved.

6

Capture marks order paid and issues scheduling token

After the capture is confirmed, Postgres records the paid status and transaction. The training enrollment receives or reuses a 14-day scheduling token, then notification emails are sent.

Payment stateEmail
Code and data

The Square training card finalizer records the paid status and captured transaction, reuses or issues the 14-day scheduling token, builds the schedule URL, and sends the Resend-backed notification emails and staff alert.

7

Student schedules the intro call

The training checkout response redirects straight to a tokenized schedule page. That page validates the token against private enrollment state before revealing the configured Google Appointment Schedule URL or iframe.

Token gateCalendar scheduling
Code and data

buildTrainingScheduleUrl, TrainingSchedulePage, resolveTrainingIntroCallEligibility, and findPendingTrainingenrollmentByToken protect the Google Appointment Schedule URL configured in Sanity. TrainingConfirmationPage is an alternate/fallback order-based entry.

Async and recovery path

Square webhook recovery/api/webhooks/square verifies the Square signature; its commerce recovery branch reconciles a COMPLETED payment.* whose reference matches a pending training order, and the capture-reconciliation cron recovers paid-but-uncaptured orders — both idempotently finalizing missing enrollment/notification/token work.
Confirmation fallbackgetVerifiedTrainingConfirmation supports the alternate confirmation page, while the main checkout response returns the schedule URL directly. Legacy /booking?type=training-call&order=... links are shimmed toward tokenized scheduling.
Privacy boundaryNo checkout token, customer PII, Square payment/order, or scheduling-token data is written to Sanity.

Flow 02

Service booking flow

A client selects an operational PostgreSQL offering and time, receives an opaque payment-session page, then pays through Square CHARGE_AND_STORE before the authoritative PostgreSQL appointment is projected to Google Calendar.

Operational Postgres + Square + Google Calendar API
1

Booking page loads operational settings and offerings

The canonical service booking route reads active public offerings, provider choices, prices, durations, add-ons, intake questions, timezone, and marketing wording from PostgreSQL. Sanity may supply linked service detail-page editorial, imagery, and SEO, but it is not the operational booking authority.

Postgres readService UI
Code and data

src/app/(site)/services/[slug]/booking/page.tsx calls loadPublicOperationalOfferings and loadOperationalBookingUiSettings. Legacy /booking links redirect to canonical service booking routes.

2

Availability resolves schedules, resources, Calendar busy time, and reservations

The browser requests slots for an offering. The server resolves the offering's provider/resources and schedules from PostgreSQL, reads busy events from assigned Google Calendars, overlays active resource reservations, and returns only valid slots.

AvailabilityCalendar readResource locks
Code and data

/api/booking/availability?offeringId=... uses loadOperationalAvailabilityContext, buildOperationalBookingSlots, and listConnectionCalendarEvents. Calendar and resource IDs are resolved server-side; the browser does not choose routing identifiers.

3

Intake answers create a private reservation and opaque payment session

The booking flow submits the offering ID, selected time, optional add-on, and intake answers. It does not collect or send customer contact or card data at this step. The server revalidates configuration and availability, creates the expiring hold/resource reservations, and returns an opaque payment-session reference plus an internal payment-page URL.

HoldOpaque handoffConflict check

4

Server resolves the payment session; page collects customer and policy choices

The no-index payment page resolves the opaque reference against the service slug and active hold. It displays trusted pricing and expiry, then collects customer details, marketing choice, deposit/full/custom-partial selection, and explicit no-show/late-cancellation policy acceptance.

Private sessionCustomer inputPolicy evidence
Code and data

resolveServiceBookingPaymentSession, ServiceBookingPaymentPage, ServiceBookingPaymentShell, and ServiceBookingPaymentForm keep the public URL scoped to the opaque session reference and a server-resolved snapshot.

5

Square tokenizes, charges, and stores the card

Square's browser fields tokenize with intent: "CHARGE_AND_STORE"; the PAN never reaches the app server. The payment confirmation route revalidates the hold, recomputes the selected amount and Ontario HST from trusted state, persists customer/marketing/policy evidence, then authorizes, captures, and stores the Square card for the accepted no-show policy.

Square SDKDirect captureCard on file
Code and data

SquareChargeAndStoreForm posts the token and verification token to /api/booking/payment/confirm. service-charge-and-store.ts validates amount, currency, idempotency, policy, and provider attribution before completion.

6

Captured evidence and the authoritative appointment are persisted

PostgreSQL records the authorized/captured payment attempt and confirms the operational appointment with Calendar status pending before external Calendar projection. A retry reuses provider evidence and resumes local projection instead of creating another charge.

Payment attemptAppointmentIdempotent
Stored in

service-booking-payment-repository.ts records booking_payment_attempts and calls confirmOperationalAppointment. Holds, appointments, saved-card references, policy acceptance, and no-show records remain private PostgreSQL data.

7

Google Calendar receives an idempotent projection

The finalizer finds or creates one event on the assigned provider calendar. Calendar connections and canonical assignments live in PostgreSQL; OAuth refresh tokens are encrypted at rest with BOOKING_CALENDAR_CREDENTIAL_ENCRYPTION_KEY. PostgreSQL remains authoritative if Calendar is unavailable.

Calendar projectionEncrypted credentialManual recovery
Code and data

calendar-connection-repository.ts, calendar-credential-secret.ts, and google-calendar.ts resolve the server-owned connection and canonical calendar assignment. Success stores the provider event ID; failure enters durable manual-follow-up state.

Booking outcomes

BookedSquare capture is durable, the PostgreSQL appointment is authoritative, the Calendar projection is synced, and the client receives booked confirmation.
Manual follow-upIf payment captured but appointment or Calendar projection cannot complete, durable provider evidence and idempotency state allow reconciliation without a second charge; staff sees the recovery state.
Fail closedIf direct service payment or its public config is disabled or unavailable, new payment sessions do not create hosted Payment Links. Holds expire normally. Legacy return/webhook handlers remain only for historical hosted-checkout reconciliation.

Shared map

Code, data, and provider boundaries

These boundaries are common across the three diagrams and are the fastest way to audit regressions.

Sanity editorial and catalog retrievalsrc/data/loaders.ts centralizes Sanity reads for product catalog, training programs, global/page content, and optional service detail-page editorial. It is not the operational service-booking configuration store.
Operational booking PostgreSQLsrc/lib/private-db/schema.ts and booking repositories own booking business/UI settings, providers, offerings, resources, schedules, exceptions, Calendar connections/assignments, holds, resource reservations, appointments, and payment attempts.
Private commerce PostgreSQLcheckout_orders, checkout_payment_events, training_enrollments, marketing/contact records, and other customer/payment evidence remain private. Neither commerce nor booking PII belongs in Sanity.
Square commercesrc/lib/commerce owns Square authorize/capture, refunds, obligation reconciliation, order persistence, webhook recovery, and product/training emails.
Square service paymentsrc/lib/booking/payments/service-charge-and-store.ts, src/lib/private-db/service-booking-payment-repository.ts, and /api/booking/payment/confirm own new service capture/card storage. /api/webhooks/square is shared with product and training.
Google Calendar projectionsrc/lib/booking/google-calendar.ts reads assigned calendars for busy time and projects confirmed service appointments. Encrypted credentials and canonical resource assignments live in PostgreSQL. Paid training separately uses a Sanity-configured Google Appointment Schedule URL.
Short-lived coordinationRate limiting, active-hold quotas, and scoped coordination locks may use Upstash, but they do not own Calendar credentials, booking configuration, appointments, or payment truth.
Resend email handoffProduct confirmations, booking confirmations, and training payment notifications are sent after private state changes; email is not the source of truth.

Provider rule

Square powers product checkout, training checkout, and paid service booking. Product and training use the Square Web Payments SDK (gated by SQUARE_COMMERCE_ENABLED); all three share the single Square webhook at /api/webhooks/square. Historical Helcim orders remain readable, but no code path creates new Helcim payments.

Privacy rule

Sanity must not store new checkout transaction history, customer PII, payment events, provider identifiers, service holds, or paid training scheduling tokens. Those records belong in private Postgres with redacted evidence.
