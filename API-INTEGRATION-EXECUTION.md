## How to use and update this document

1. Before starting work, read the relevant plan sections, this tracker's current position, the task's prerequisites, and the applicable repository instructions. Reconcile contradictions with current code and recorded decisions before changing behavior.
2. Select the earliest unfinished phase. Within it, choose a task whose dependencies are `DONE`. Rows are the recommended order; tasks with satisfied dependencies may proceed independently. Every dependency is required. A phase gate stands for all work and evidence in that phase.
3. Set the selected task to `IN_PROGRESS` and add an entry to the work/evidence log with the responsible person or chat, date, repositories, and intended verification. Update the current-position table. Keep stable task IDs when splitting or revising work; add new IDs rather than renumbering completed history.
4. After implementation, use `VERIFYING` until the listed checks have run. Mark `DONE` only when the completion criteria are met, evidence is recorded, and necessary contract, migration, configuration, and operational documentation changes are accounted for. A task that requires deployed or provider evidence cannot close with only unit tests.
5. After each completed item, failed check, blocker, or dependency change, update its status and log immediately. Record exact revisions or immutable artifacts, commands and outcomes, environment, remaining limitations, and any follow-up IDs. For cross-repository work, identify all affected revisions. Never include secrets, customer data, or payment tokens.
6. Re-evaluate dependent tasks and phase gates, then update the next action and last-updated date. Record a concrete unblock condition for `BLOCKED`; do not silently waive prerequisites or mark a partial task complete. Keep blockers in this tracker until evidence resolves them.
7. When a dependency changes after certification, return affected tasks/gates to `VERIFYING` and record why their evidence is stale. A passed gate applies to its recorded revisions and environment, not every subsequent build. Evaluate scope changes in the plans first, synchronize all three copies, and adjust this tracker in the same work.

`NOT_STARTED` means no verified completion is recorded; `IN_PROGRESS` means active work; `VERIFYING` means implementation awaits required evidence; `BLOCKED` means a named dependency or decision prevents progress; `DONE` means the recorded criteria passed. Task ownership below is a repository or operating responsibility, not an assigned individual.
